## 3. 数据层：`trainingdata/`（初加工产物）

**四块产物，按年份分区**（2026-09-20 **下午**由七块收敛而来）：

```
trainingdata/
├── meta.json                            清单 / 边界 / 上游指纹 / 逐年摘要 / 覆盖率 / 各块指纹
├── factors/year=YYYY/data.parquet       trade_date, stock_code, <337 个特征>   ← 全部因子
├── target/year=YYYY/data.parquet        trade_date, stock_code, <5 个 target>  ← 全部收益
├── amount/year=YYYY/data.parquet        trade_date, stock_code, amount         ← 每日成交额（元）
└── fac_sample/year=YYYY/data.parquet    trade_date, stock_code, <20 个抽样特征>
```

| 块 | 装什么 | 谁用 | 动它会改 `panel_digest` 吗 |
|:--|:--|:--|:--|
| `factors` | 全部特征的**当日截面 rank**，方向已统一成"越大越好" | 训练/评价 | **会** |
| `target` | **1d / 3d / 5d / 10d / 20d 五个 target**（`label_ret_*d`）的收益原值 | 训练/评价 | **会** |
| `amount` | 每日**成交额（元）**，用户口径叫"市场所有的流动性" | 回测/策略 | 不会 |
| `fac_sample` | `factors` 里**随机抽 20 列**（seed=42），值逐字取自 `factors` | 冒烟/最小输入 | 不会 |

### 2026-09-20 下午删掉的三块，以及为什么

| 删掉的 | 为什么 |
|:--|:--|
| `universe` | **实测 4,475,340 行里 `in_universe=False` 0 个**。轴就是那 2115 只冻结池（`build_axis` 取 `Engine.codes`），掩码是同一批代码过上游 `universe_for`，而冻结口径（主板 ∩ 至今存续 ∩ 从未ST ∩ 上市≤2018-01-01）保证它必然全 True —— **恒等掩码，没有信息**。顺带发现它以前还是**白算**的：掩码根本没进 `_coverage`（那只吃 `factors`），算完只被原样写盘 |
| `P` | 价格/成交量**原料**（81 MB）。不在布局里；★ **构建它的代码也于同日删掉了**，回测要用得先把它加回来 |
| `sample/` | 同构小样本树（500 只 × 近 2 年，128 MB）。**构建代码同样已删** |

★ 删 `P` 之后 `amount` 反而更重要：`amount` 与 `P.amount` 实测**逐位相同**（9 年逐年核对），
所以删 `P` 之前它是冗余列，删之后它是成交额的**唯一**存放处。

★ **`panel_digest` 只哈希 `columns.features` + `columns.labels` + 逐年 `files.factors.sha`。**
哈希串里**不含块名**（块名只用来查 key），所以**块改名本身不换锚点** —— 但前提是
`preparingdata.py` 的块名常量与 `meta.json` 的 key **同步**改；只改一头会**静默换掉锚点**
（实测：漏改会得到 `d90b20cf37710f94`，正确值是 `798ccb32214853a8`）。
于是 `amount` / `fac_sample` 是**只增不改**的 —— 补建它们不会作废任何结论。
反过来，`factors` / `target` 一变，锚在这个指纹上的结论**全部要重跑** ——
★ 注意**改 `columns.labels` 的顺序也算变**（那个列表直接进哈希），所以别顺手"整理列序"。
这条界线要守住。

★ **`fac_sample` 同时登记进 `meta.feature_sets["sample_20"]`** ⇒ 单元只写
`DATA = {"features": "sample_20"}` 就能对 `factors` 做 20 列的快速冒烟，
**引擎完全不需要知道 `fac_sample` 这个物理块的存在**。
（`sample_20` 是**特征集名**不是块名，所以这次块改名没跟着改。）

### 三个口径（都是踩过坑才定的）

1. **权威网格 = 交易日历 ∩ [上游产物实际最早/最晚日] × Engine.codes，缺格写 NaN**，覆盖率进 meta。
   实测上游几百个因子**并非逐格一致**（晚起点因子早年缺天、末尾参差）——
   "不一致就报错"的老写法在放开全历史时必然误报，所以改成"对齐 + 覆盖率报告"。
   ★ 端点一律取**产物**的实际日期，**绝不用交易日历**（日历含未来 16 个交易日）。
2. **`factors` 存 `rank` 列并把方向烘焙进来**：`higher_is_better=False` 的因子存 `1 − rank`，其余存 `rank`。
   语义统一成"越大越好"，值域仍是 [0,1]。**`target` 存标签 `value` 原值，不翻方向。**
   ★ 为什么不是 `−rank`：旧写法把翻转列变成 [−1,0]，再被 `clip(0.001,0.999)` 一夹就**整列压成常数**
   —— V1 时代 83 个因子（37%）就是这样被抹平的（见 [VERSIONS.md](VERSIONS.md) §8）。`1−rank` 恒在 [0,1]，不可能再出这种事，
   而且 0.5 在两种表示下都是缺失的中性填充值。
3. **`meta.json` 最后写**：中途失败时下次能从旧 meta 正确重算，不会把"半新半旧"当已完成。

★ **`P` 若重建，存的仍是"原料"而不是算好的复权价**：上游 `hfq_X = ffill(X) × ffill(adj_factor)`
是逐点乘积，而 `ffill` 的效果**取决于作用窗口** —— 若在导出时就把 `hfq_*` 算死，等于把"导出窗口"
焊进数据，消费端换一个读取窗口首行就对不上了。存原料、由消费端在**它自己的窗口内**套用同一套
运算，才逐位保真。★ `P` 已于 2026-09-20 从布局里删掉、构建代码也删了（见上文）；
这条口径留给将来若要把价格层加回来时参考。

### 增量更新（`preparingdata.py`）

- 窗口 = `[上次末日 − lookback, 上游最新日]`，**只重写窗口覆盖到的年份分区**，未触及的年份零 I/O；
  "上游没有新东西"走零 I/O 快路径直接跳过。
- `lookback` 默认 = **最长标签的 h + 1 + 冗余 7**（= **28 个交易日**，2026-09-20 瘦身时定的口径）。
  ★ `h + 1` 是**硬下限**：标签 `T` 用到 `open(T+1+h)`，要等 h+1 个交易日才定型；窗口比这短，
  那些天一旦出窗就**再也不会被重算**，20d 标签会永久停在 NaN。
  ★ `+7` 是**冗余覆盖**（用户要的）：即使标签已定型，也把那 7 个交易日重算一遍，吃掉上游的小幅回改。
  ★ 为什么**不**写成"每个标签各自刷最新 7 个有效行"：跨度大时会漏 —— 若上次跑在 30 个交易日之前，
  20d 标签是在 `T_max−51 ~ T_max−21` 里陆续定型的，只刷最新 7 行就漏掉 `T_max−51 ~ T_max−29`。
  `上次末日 − lookback` 这种写法对任何间隔都成立。
- 上游**回填历史**（新增年份分区）由指纹里的 `per_factor_years` 发现 → 那些年份整年重建。
- 增量只重算**窗口覆盖到的年份**，未触及的年份零 I/O；窗口外的行从既有分区读回来原样拼在前面
  （`_load_keep`），所以增量与全量的产物**逐字节相同**（2026-09-20 实测过）。
- ★ **`P` 与小样本树的构建代码已随瘦身删掉**，不会再自动长回来 —— 它们原先挂在
  `prepare()` 的两条路径上，跑一次不带参数的 `preparingdata.py` 就会把 81 MB / 128 MB
  悄悄恢复，与四块布局矛盾且不报错。

### 命令

```bash
PY=/autodl-fs/data/miniconda3/bin/python        # ★ 必须全路径
cd /autodl-fs/data/model

$PY preparingdata.py                 # 自动：没有产物→全量；有→增量（日常就这一条）
$PY preparingdata.py --full          # 全量重建
$PY preparingdata.py --years 2025 2026             # 只加工指定年份
$PY preparingdata.py --check         # 只校验：meta↔文件↔上游 + 取值域抽查（日常第一条）
$PY preparingdata.py --amount-only   # ★ 只补 amount（每日成交额），不改 panel_digest
$PY preparingdata.py --fac-sample-only     # ★ 只补 fac_sample（因子抽样），同上
$PY preparingdata.py --meta-only [--freeze]  # 只补 meta 派生字段（不读因子侧、不碰数据文件）
$PY preparingdata.py --jobs 8        # 读并发（默认 6；共享盘上别开大）
$PY preparingdata.py --out trainingdata_new --full   # 写到另一份目录（现有产物一字不动）
$PY preparingdata.py --features-from <meta.json>     # 锁定特征清单（与旧产物逐位对拍用）
```

> ★ **日常就一条命令**：`$PY preparingdata.py` —— 有上游新数据就走增量、没有就零 I/O 跳过。
> 增量窗口 = 上次末日往前 **28 个交易日**（= 最长标签 h + 1 + 冗余 7，见模块 docstring）。
>
> ★ 快照**当前不是冻结状态**（2026-09-20 瘦身时解冻，否则日常命令会被闸门拦住）。
> 要重新上锁 / 解锁：`--meta-only --freeze` / `--meta-only --unfreeze`（**只翻标记，
> 不重建、不换指纹**）。

★ **`preparingdata.py` 是单文件独立脚本**，不 import 项目内任何模块，只依赖
numpy / pandas / pyarrow + 上游 `fea`。换机器交接时，一个文件就是全部。
上游路径可用 `MX_UPSTREAM` / `MX_FACTORS_DIR` / `MX_FACTORS_STATE` / `MX_RAW_DATA` 覆盖。

### ★ 换数据（快照）的正确姿势

**另建 → 体检 → 换，别原地覆盖**：

```bash
$PY preparingdata.py --full --out trainingdata_new     # 另建，现有产物一字不动
$PY preparingdata.py --check --out trainingdata_new    # 先体检（支持指定目录）
mv trainingdata trainingdata_bak_<日期> && mv trainingdata_new trainingdata
```

★ 为什么不原地覆盖：所有已出结论都锚在旧 `panel_digest` 上，覆盖掉就**没有对照组**了。
代价只是几 GB 磁盘（同盘 `mv` 瞬时）。

★ 冻结闸门**不挡这条**：`--out <新目录>` 那个目录还没有 `meta.json`，闸门读不到锚点就放行
（闸门只拦"往已有快照上重建"）。所以冻结期间依然可以另建再换。

### ★ 上游会变，而且不一定会通知你（2026-09-20 血的教训）

**上游因子工程在 2026-09-19 之后被整体重算过，下游没有收到任何通知。** 实测到的变化：

| | 旧快照（2026-09-19 建） | 上游现在 |
|:--|:--|:--|
| 覆盖 | 2012-01-04 ~ 2026-09-18 | **2018-01-02** ~ 2026-09-18（2012~2017 分区被删） |
| 因子数 | 306 个特征 | **337** 个特征 |
| 台账文件 | `log0918_post/dayhash.tsv` | 目录改名成 `logs/`，该文件不存在 |

**而且变的不只是范围**：拿 2026 年逐格比对，306 个特征里 **265 个逐位相同、41 个有差异**，
差异的**全部是财报类因子**（`asset_growth_qoq` / `rd_intensity` / `yoy_revenue` / `net_margin_ttm` …），
每个覆盖约 36.76 万格、平均绝对差 0.0005 ~ 0.0017 —— 这是**财报数据被厂商重述后整段回填**的特征。

⇒ **任何用旧数据训练出来的模型，它的基本面输入已经过期。**

**差点造成事故的一条路径**：在旧快照上跑一次不带参数的 `python preparingdata.py`（日常命令）
会这样走 —— 上游指纹变了 → 不是快路径 → 31 个新因子在 2018~2026 都有分区 ⇒ 这 9 年**整年重建**
（用新的 337 列），而 2012~2017 仍留 306 列 ⇒ 得到一个**半新半旧的嵌合体**
（`factors` 分区列数不一致、meta 声称 337 列但轴只剩 2018 起），**而且不报错**。

**处置**：先把旧快照显式冻结（`--meta-only --freeze`，锚点 + 原因写进 meta），
任何重建路径当场被拒；然后按用户裁定**整体重建**并对齐上游。
`meta.json` 的字节备份留在 `/tmp/trainingdata_meta_pre_refactor_20260920.json`。

**教训**：`--check` **抓不到"上游丢了一批历史数据"** —— 它只比对"上游最新日 / 最早日"
与产物的边界，上游把早年分区删掉时它认为"上游变晚了"而不是"出问题了"。
所以**换机器或长时间没跑之后，先看 `--check` 输出里的"上游扫描：N 个因子 · 分区年 M 个"
与 meta 里记录的数目对不对得上**，再决定要不要重建。

### 仍需现读上游的两处

训练链路（`run` / `split` / `eval`）**完全不碰上游**，只读 `trainingdata/`。
仍会现读的只有两处，引用它们的结论要标注"上游可能已变"：

- `mx/preprocess.py::screen_report` —— 读模块② 的 eval summary（纯报告，不影响数值）；
- `mx/backtest.py` / `mx/strategy.py` —— 原读价格层 `fea.panel` 算真实收益与可交易性。
  ★ 2026-09-20 **上午**曾改为读 `trainingdata/P`（`mx/prices.py`）；**同日下午 `P` 随四块收敛
  被从快照里删掉**，于是回测**现在没有价格来源** ——
  要用回测就得先把价格层加回来（`P` 的构建代码已随瘦身删除）。在那之前这条路径该**硬失败**（宁可崩掉，
  也不要像 D5 那次一样被 `except` 静默降级成"不套可买掩码"、给出看着正常的错数字）。

### ⚠️ 2026-09-18 深夜：因子侧冻结股票池 → 回测路径静默错位（已加硬闸门）

> **2026-09-20 补注**：本节那道闸门（`mx/upstream.py::assert_price_axis`）所在的顶层 `mx/`
> 已在上午的重构里删除；而**价格层本身在下午随 `P` 块一起从快照里删掉了** ——
> 也就是说"轴错位"这类事故现在**没有载体**了（没有价格层可错位）。
> 保留下面的记录是因为**「面板代码轴 ≠ 上游引擎轴 ⇒ 静默错位」这条机理是通用的**：
> 任何重新引入价格层的方案（把 `P` 加回来）都必须把这道校验一起带回来。

因子侧按用户拍板把股票池从「主板全集 + 动态进出」3485 只改成**固定名单 2115 只**
（主板 ∩ 至今存续 ∩ 从未ST ∩ 上市 ≤ 2018-01-01；**代价是幸存者偏差，用户已确认接受**）。
`Engine.codes` 已经变成 2115 —— 而本模块的快照仍是旧口径的 **3484 只**。

**后果（实测，不是推测）**：`fea/prices.py::_place_from` 把价格按「引擎位置」落格，再由
`Panel.place` 按**列号**写进调用方的面板 —— **只要面板的代码轴与 `Engine.codes` 不一致
（集合或顺序任一不同），价格就会静默错位**：甲的价写进乙的列，不报错、不出 NaN。
实测旧快照：列 2 的 `000003.SZ` 拿到 `000006.SZ` 的价、列 1000 的 `002377.SZ` 拿到 `002911.SZ` 的价。
⇒ **在旧快照上跑的任何策略/回测结论都是错的**（IC 层不碰价格层，不受影响）。

**已加闸门**：`mx/upstream.py::assert_price_axis(cfg, codes)`，在 `strategy.price_ctx` 与
`backtest._price_arrays` 进入价格层之前硬校验（两向都验过：旧轴被拦、引擎轴通过）。
报错信息里写了三条出路：

1. 只看 IC 层 → `main.py analysis <单元> --no-backtest`（训练/IC 完全不碰价格层）；
2. 在新口径下重建快照 → `preparingdata.py --full --unfreeze`（面板指纹会变，旧结论全部重跑）；
3. 要保住旧快照的回测 → 需要让价格层支持**任意代码表**（`PriceLayer(up, cfg, cal, codes)`
   本身就支持，只是引擎只传自己的），或把 `price_ctx` 改成"按引擎轴算、再按面板代码 gather"
   （内存有界，约 60 MB/字段）。**这条路要不要走，等用户拍板。**

★ 顺带的发现：小样本树（500 只）跑回测**本来就**是错的（同一类错位，只是以前没人发现）。
现在会被闸门挡住 —— 冒烟要看回测请用全快照，或加 `--no-backtest`。

### ★ 新旧快照**不可直接比**（幸存者偏差，2026-09-19 起）

> **2026-09-20 补注**：本节讲的那两份旧数据（3484 池归档与 306 特征新池快照）**都已删除** ——
> 用户裁定"数据只需要对齐上游，上游删了这里也没必要留"。保留下面的推理是因为
> **「跨池/跨特征集不可比」这条纪律永远成立**，而且**2026-09-20 又发生了一次同类事件**
> （上游重算因子 ⇒ 特征集与年份范围都变 ⇒ 旧结论再次全体作废，见 `LOG.md`）。
> ★ 教训升级：不只是"跨池不可比"，而是**"任何一次上游重算都会让下游结论作废"** ——
> 所以每次引用旧结论前，先核对它建在哪个 `panel_digest` 上。

因子侧 2026-09-19 完成口径切换：股票池 = **固定名单 2115 只**（主板 ∩ 至今存续 ∩ 从未ST ∩
上市 ≤ 2018-01-01），全量重算后 **2,160,796,095 行**、零池外残留、`增量==全量` 复测 0 不一致。
旧快照（3484 池，含退市与曾 ST 股）保留为归档对照组。

⇒ **跨这次切换的净值/回测数字一律不可比**：新口径要求"至今存续"，等于事前剔除了后来退市/长期
ST 的股票，**绝对收益被系统性抬高**（用户已确认接受这个代价）。要比较，只能在**同池内部**比
（旧归档 vs 旧归档、新快照 vs 新快照），或明确标注"跨池不可比"。
IC 层同理会受影响（截面变了、排名变了），但**方向性结论**通常比绝对水平稳，引用时仍要注明池子。

### ★ 2026-09-20 下午：块改名（`X`/`Y`/`sample_input` → `factors`/`target`/`fac_sample`）

（`amount` 不变），同时删掉 `universe` / `P` / `sample/`（见上文的"删掉的三块"）。

**T1/T2（价格轴错位）—— 已无载体，保留机理。**
根因：上游 `fea/prices.py::_place_from` 用「引擎位置」落格、`Panel.place` 按**列号**写进调用方面板，
**默认了**调用方的代码轴 ≡ `Engine.codes`（一个从没写下过的隐式契约）。
根治方向：出口按**代码**对齐（`searchsorted` + gather），或在写之前校验两轴一致并**直接报错**。
★ 现状：`P` 块已删、价格层没有载体，这类事故暂时不会发生；但**任何把价格层加回来的方案
都要把这道校验一起带回来**。另：池子固定 2115 只后 `Engine.codes` 不会再变（冻结的目的），
而**只要冻结名单被编辑，`universe_fp` 就会变** —— 它是 `prepare()` 判"要不要全量重建"的锚点。

**T3. ★ `stock_daily.stock_name` 不是历史名称 —— 别用它判 ST/风险**
上游实测：厂商把**整段历史**的名称都改写成了**当前**名称。实例 `000004.SZ`：
`stock_st_info` 说它 2022-05-06 起才是 `ST国华`，而 `stock_daily` 里**全部 3724 行
都是 `国华退`**（当前处于退市整理期的名字）。
后果：用名称判"曾经 ST"只找到 **284** 只，官方口径是 **784** 只，**漏 502 只**。
判 ST 请用 `stock_st_info`（`type='ST'`）；判板块用代码前缀。
（`model/` 下若只是拿它做展示无所谓，**别进特征/筛选逻辑**。）

**T4. 冻结池的 IC / 收益**不可跨这次变更前后比较**
池子把**退市股与曾 ST 股**永久移出评价域 —— 而它们正是长期最差的一批。
⇒ 同一因子在新池里的 IC 会**系统性偏乐观**，新池净值也不可与旧池净值直接比。
这是"可复现性优先"换来的代价（用户已确认接受），不是 bug。
**做 A/B 时请确保两侧同池**，否则结论无效。
