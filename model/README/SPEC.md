### 两层数据

```

```

`preparingdata.py` 是**唯一的写入口**；模型侧（各单元的 `mx/`）**只读** `trainingdata/`，

### 三段代码职责

| 层 | 在哪 | 是什么 |
|:--|:--|:--|
| **构建期** | `preparingdata.py` | 读上游、建四块产物。**不交付**（天然依赖上游 17 GB） |
| **引擎** | `<单元>/mx/` | 数据/切分/预处理/评价/回测/产物契约。**随单元走**，每个单元一份 |
| **单元** | `<单元>/model.py` | 本版架构与配方的**唯一权威定义** |

### ★★ 独立单元：定义与边界（2026-09-20 用户再次强调）

> 用户原话：「这个文件夹**不依赖任何其他的脚本**，除了读取外部的数据源 `trainingdata`。
> 这个文件夹自身所有的训练代码都是**不依赖 `Vi` 以外的外部文件**就能够完成模型的训练与回测的。」

**定义**：把 `<单元>/` 整个目录压缩发出去，收件人装好依赖、给一份 `trainingdata/`，
就能跑完**训练 + 评价 + 回测** —— 不需要本仓里的任何其它文件。

**做到这件事靠三样：**

1. **引擎随单元走** —— `<单元>/mx/` 是引擎的完整副本（**不含** `prepared.py` / `upstream.py`，
   那两个是构建期模块，只在 `preparingdata.py` 里）。`mx/config.py` 里
   `ROOT = Path(__file__).resolve().parent.parent` 这条规则让「引擎复制到哪，哪里就是根」，
   所以单元代码不用感知自己被放在哪。
2. **数据根三候选解析**（`mx/config.py:_resolve_trainingdata`，**判据是 `meta.json` 存在**）：
   `$MX_DATA` > `<单元>/trainingdata` > `<单元>/../trainingdata`。
   ⇒ 打包发送时把数据放进单元目录；在模块根下原位跑就用同级那份。
   ★ **判据必须是 `meta.json` 而不是「目录存在」** —— 任何一次 `mkdir(trainingdata)`
   都会造出空目录，让单元永远读不到真数据，而报错还是「没有 meta.json」，把排查指到错的地方。
3. **入口按本目录定位引擎** —— `run.py` / `analysis.py` 写的是
   `ROOT = Path(__file__).resolve().parent`（**不是 `parents[1]`**）。

**能力边界（要跟收件人说清）**

| 能做 | 不能做 |
|:--|:--|
| 训练、打分、IC 评价、策略推演、回测<br>⚠️ **截至 2026-09-20 尚未跑通** —— `mx/` 还读旧块名（`X`/`Y`/`universe`/`P`），见 [TODO.md](TODO.md) §12 第 0 条 | **重建 `trainingdata/`** —— 那要读上游几百个因子，是构建期职责，只在模块根提供 |
| 改 `model.py` 配方后重训 | 拿到上游因子侧的任何东西 |

cd <单元> && $PY main.py doctor     # 环境自检（$PY = /autodl-fs/data/miniconda3/bin/python）

## 2. ★★ 防泄漏铁律

**铁律一：时序切分必须 purge + embargo。**
标签是前视的（`label_ret_hd(T) = open(T+1+h)/open(T+1) − 1`），相邻交易日样本**共享未来 h 天行情**。
所以边界两侧各让开 `h` 个交易日：**purge**（切点前的样本标签伸进了测试期）+ **embargo**（切点后的
特征与训练期末尾强相关）。**禁止随机切分**（`mx/dataset.py` 里没有随机分支）。

**铁律二：一切统计量只用当日截面。**
不许出现全样本 `mean/std/quantile`（标准化、填充、缩尾都不行）—— 那是未来信息。落点：
特征用 `rank`（初加工已做成当日截面百分位）；线性模型缺失填**固定常数 0.5**（不用当日中位数）；
集成是**逐日截面 z**；打分是**逐行**的（由 `main.py audit-pit` 的**截断复算**守这条）。
新增的标签变换与样本权重（`mx/labels.py`）同样遵守，且逐条在函数注释里写明理由。

**★ 铁律三：一切 top_ret 口径必须套"买得进"掩码，且掩码必须对齐到【成交日】。**
（2026-09-18，两条血的教训，第二条更贵）

不看可执行性的 top_ret 会**奖励"挑明天一字涨停"的模型**：模型专挑"T 日收盘涨停"的票
（占 top1 的 35.3%），这类票 T+1 开盘大概率一字、**买不进**。实测 V3 折 1
（`gbdt_w/5d`，253 天）：不套掩码 Σtop1 = **+3.777**，套上**对齐正确**的掩码 = **−1.576**
（复利 −87%）。

★★ **而且"套了掩码"还不够 —— 掩码必须对齐到成交日 T+1，不是信号日 T。**
`analyze` 原先传的是 `entry_ok[T]`（= "昨天能不能买"），恰好放过了模型专挑的那批票，
于是主判据**系统性偏乐观约 2.2 个 Σ 单位**（+0.637 vs 正确的 −1.576）。
**这类错位不报错、不崩、不看两套口径对不上就发现不了** —— 详见 [VERSIONS.md](VERSIONS.md) §8.5。

这不是交易摩擦（费用/滑点），是**可执行性**，属于硬约束 #4（可交易性归模块③）。
落点：`evaluate.costfree_cumsum(enterable=...)`，调用点必须走
`analyze.entry_mask_next_day()`；`mx/analyze.py` 默认路径一律传真实可买掩码。
★ 2026-09-20 用户拍板：**拿不到价格层就硬失败，不许静默降级**（原来的"打一行 ⚠️ 并标
`exec_filter=False` 继续跑"是被否掉的写法 —— 见 [EVAL.md](EVAL.md) §7）。

## 4. ★ 切分口径：研究单元 vs 实战单元（用户 2026-09-17 拍板）

| | **研究单元 `V{N}`** | **实战单元 `best`** |
|:--|:--|:--|
| test 集 | **固定窗 2025-09-01 ~ 2026-09-01**（样本外，用来打分/回测/判定） | **没有** |
| train+valid | 只能用 **2025-08-10 之前** | **全部数据**（train_end 放到数据末日） |
| 用途 | 比版本、出结论 | 出当下的选股打分 |

- 单元在自己的 `model.py` 里用 `SPLIT = {...}` 声明切分（配置的权威定义在单元）。
- **隔断由 purge 自动保证**：标签 `T` 用到 `open(T+1+h)`，所以每个标签的
  **effective train_end = min(train_end, test 起点 − (h+1) 个交易日)**。
  实测（V2 时代，旧数据）：20d 标签退到 **2025-08-01**、5d/1d 停在 **2025-08-08**
  ★ **这组数字已不可复现** —— V2 已归档且无引擎。要复现请用 `V16`：
  `cd V16 && $PY main.py split V16`。
- **`best` 的生产口径由引擎施加**（`mx/unit.py:Unit.split_cfg`：单元名是 `best` 或声明了
  `PRODUCTION=True` ⇒ 丢掉 test 窗、train_end 放开）。这样 `main.py promote V{N}` 就能保持
  **纯文件复制**，不会把研究口径的 test 窗一起搬进实战。
- 多折：test 窗**固定不动**（全折共用 ⇒ 指标可比、不泄漏），valid 窗在可训练段内**等距轮换**。
  ★ 折必须同时换**数据划分**：线性模型给定数据是确定性的，只换种子会得到 4 份一模一样的模型
  （V1 首跑实测 ridge 四折 test RankIC 完全相同 —— 一个假的多折）。

## 6. 训练纪律

| 项 | 规则 | 依据 |
|:--|:--|:--|
| 折并发 | **cgroup 内存 × 0.8 / 单折实测预算** → 见下 | 超限被系统 KILL，**无警告** |
| 单折线程 | 容器可用核数 × 0.8 / 并发 | BLAS/LightGBM 互相踩踏 |
| 线程数 | 一律 `/autodl-fs/data/miniconda3/bin/python` + `MX_THREADS` 环境变量 | 容器预置了 `OMP_NUM_THREADS=12`，会**骗过 `nproc`**（报 12，实际 48 核） |
| 训练日志 | `V{N}/logs/fold<k>.log`，末尾 `EXIT:0` = 成功（续跑判据） | 与参考工程一致 |
| 清产物 | `bash train.sh --clean`（在单元目录里跑；换架构/改特征后**必须**清） | "文件已存在即跳过"会掩盖重构回归 |
| 产物分树 | 正式 / `smoke_*` 两棵树 | `--smoke` 的快看结果**绝不能覆盖**正式 artifacts 与榜单（promote 读的就是榜单） |

### ★ 内存纪律（**2026-09-18 换机器后重测，数字与旧版完全不同**）

本容器现状：**cgroup 上限 90 GiB · CPU 配额 25 核 · RTX 4080 32 GB · 磁盘 200 GiB**
（旧 README 写的 60 GiB / 32 核 / 3080Ti 是上一台机器的，已作废；
2026-09-18 上午那版写的「48 核 · 3080 Ti 12 GB · 153 GiB」又是更早一台 —— **这台机器上所有
资源数字都要现测**，`main.py doctor` 是唯一可信入口）。

| 口径 | X 体积 | **单折实测峰值** | 可并发 |
|:--|--:|--:|:--|
| 2018 起（V2b/V3/V5 现行口径） | 6.6 GiB | **≈ 20.7 GiB**（2026-09-18 重测，见下） | 2 折（**可放到 3**） |

★★ **2026-09-18 重测：单折峰值从 32.5 → ≈20.7 GiB，`_FOLD_MULT` 该从 4.9 改到 ~3.2。**
两折并发时 cgroup `anon` 峰值实测 **41.45 GiB**（`/tmp/memlog.txt` 每 15 s 采样），
⇒ 单折 ≈ 20.7 GiB ⇒ 倍率 ≈ 3.1。
**变小的原因是线程数**：旧值 32.5 GiB 是在 **89 线程**（错用了宿主核数）下测的，
直方图/多线程缓冲按线程数摊；修成 **10 线程**后缓冲小了一大截。
⇒ 按新倍率，引擎会算出 **3 折并发**（90×0.8/21.1 = 3.4），3 折峰值约 62 GiB，离 88 GiB 的
`memory.high` 还有 26 GiB 余量；**4 折（~83 GiB）不要碰**。
★ 本轮**没有改** `_FOLD_MULT`（改它会让 V3/V4/V5 落在不同的引擎哈希上，
而本轮的全部意义就是"同一引擎下可比"）。**留给下一轮**：改完先单折实测复核一次。

- **怎么测的**：本机是 **cgroup v2**（`memory.max` / `memory.stat: anon`），
  看不可回收内存读 `anon`（`file` 是可回收的页缓存，不算余量）。
  ★ 上一台是 cgroup v1（没有 `anon`，要看 `rss`）—— **两套写法都要能读**，
  `mx/unit.py:cgroup_mem_gb` 两个路径都试。
- **倍率是实测不是推的**：`mx/unit.py:_FOLD_MULT = 4.9` 来自"32.5 GiB ÷ 6.6 GiB"。
  峰值出现在 **LightGBM 那段**（它要把训练段转成自己的分箱 Dataset）。**换配方后必须重测**。
- **并发是估算出来的起点**：`main.py doctor` / `train.sh` 给的是估算值，
  真跑之前先单折实测一次，再决定并发。
- 训练前的自查顺序：`main.py doctor` → `main.py split {V}` → 单折跑一遍看峰值 → 再上并发。

#### ★★ 线程数必须按 **cgroup CPU 配额** 算，不是按亲和集（2026-09-18 修，实测踩到）

这台容器的 `sched_getaffinity` 放行**宿主 224 核**，但 cgroup `cpu.max = 2500000 100000`
= **25 核的额度**。旧的 `default_threads` 只读亲和集 ⇒ `int(224×0.8/2)` = **89 线程**，
LightGBM/BLAS 会在 25 核的额度上开 89 个线程互相踩踏。

修法：新增 `mx/unit.py:avail_cores()` = `min(亲和集, cgroup cpu.max 换算的核数)`（v1/v2 都读），
`default_threads` 与 `main.py doctor` 改用它。修完 `default_threads(2)` 从 89 → **10**，
实测单折耗时从 ~19 分钟降到 **~12 分钟**（V2b 折 1：761 s）。
★ 教训：`os.cpu_count()` / `sched_getaffinity()` 在容器里都**只反映宿主机**，
`nproc` 反而读对了 cgroup 配额 —— 判断可用核数一律照 `nproc` 的语义来。

## 6.5 ★ 损失函数引擎（2026-09-18 新增，`mx/labels.py` + `mx/losses.py`）

### 问题陈述

实盘只买 5 只，但 MSE 均匀地关心当日截面的 3000 只 —— **截面的头部决定 top_ret，
中部只决定 IC 的分母**。要同时抬 IC 和 top_ret，就得把"优化预算"往头部挪，
并把标签换成与"排序"这个真实任务同构的形式。这就是用户第 4 条要求（"综合设计 loss 函数"）的落点。

### 四件武器（可独立开关，由单元的 `heads()` 声明）

| # | 组件 | 实现 | 语义 |
|:--|:--|:--|:--|
| ① | **截面秩高斯化标签** | `labels.cs_rank_gauss` | `Φ⁻¹(当日分位)`，有界（±4）、分布稳定、与"排序"同构；掐掉涨停/重组那类把 MSE 拉爆的极端值 |
| ② | **时间衰减权重** | `labels.day_decay` | `0.5^(age/half_life)`，按**交易日序号**算（不是日历天）。市场结构在漂移，2018 的样本不该和 2025 等权 |
| ③ | **尾部权重** | `labels.tail_weight` | 当日截面最头部的 `frac` 权重 ×(1+boost)。排序依据用**原始收益率**（"头部"的投资含义只在原值次序下成立） |
| ④ | **顶部可微目标** | `losses.softmax_top_loss_np` / `nn._batch_softmax_top` | `L = −Σ pᵢzᵢ`，`p = softmax(s/τ)` **当日截面内**归一。τ→0 逼近"买 top-1"，τ 适中逼近"买 top-k" |

**为什么第 ④ 条最关键**：它把"策略目标"直接翻译成了可微损失。
`∂L/∂s_j = −(1/τ)·p_j·(z_j − S_d)`，含义是"**预测分越高的股票，模型越该为它的排序误差负责**"。
`z` 取秩高斯时它逼近排序质量（IC 侧），`z` 取真实收益率时它逼近组合收益（top_ret 侧）——
**同一组参数、同一条式子，IC 与 top_ret 的耦合就在这里**。

### 树侧为什么用"顶部焦点 MSE"而不是 `L_top` 的真梯度

树模型的损失必须是"每行一个梯度、每行一个 Hessian，且 Hessian > 0"。
`L_top` 的真 Hessian 是 `−(1/τ²)·p_j·(z_j−S)·(1−2p_j)`，**符号不定**，只能靠取绝对值硬掰，实战会抖。
所以树侧用 `losses.top_focus_grad_hess`：`L = Σ pᵢ(ŷᵢ−yᵢ)²`，`p` 按当前预测算但对求导视作常数
（IRLS / Gauss-Newton 的标准做法）⇒ 梯度 `2p_j(ŷ_j−y_j)`、Hessian `2p_j` **恒正**。
语义上它关心"头部的**分值**准不准"，`L_top` 关心"头部的**收益**对不对"—— 两者都试，让榜单裁决。

### 模型族（`mx/models/`）

| 类型 | 类 | 目标 | 权重 | 分组 | 设备 |
|:--|:--|:--|:--|:--|:--|
| `linear` / `linear_w` | 岭回归 | 任意 / 秩高斯 | — / ✓ | — | CPU（224 维闭式解，秒级） |
| `gbdt` / `gbdt_w` | LightGBM | 任意 / 秩高斯 | — / ✓ | — | CPU（官方 wheel 无 GPU） |
| `gbdt_rank` | LightGBM `lambdarank` | 当日收益等级 | ✓ | ✓ | CPU |
| `gbdt_focus` | LightGBM + 自定义目标 | 顶部焦点 MSE | ✓ | ✓ | CPU |
| **`xgb`** | XGBoost | 秩高斯 | ✓ | — | **GPU**（实测快 3.4×） |
| **`xgb_rank`** | XGBoost `rank:ndcg` | 当日收益等级 | ✓ | ✓ | **GPU** |
| **`nn`** | PyTorch MLP | 混合损失 | ✓ | ✓ | **GPU** |
| **`nn_v8`** 🆕 | 线性排序头（ridge 热启动）+ 小 MLP 顶部分支 | −3·(IC+软秩RankIC) / 软TopRet+ListNet@20 | ✓ | ✓ | **GPU** |
| **`nn_wpcc`** 🆕 | MLP(256→128) | wpcc（按**预测名次**几何衰减加权的 Pearson） | — | ✓ | **GPU** |

★ `nn_v8` / `nn_wpcc` 是**参考工程复刻**（2026-09-19，见 [VERSIONS.md](VERSIONS.md) §8.10），实现在 `mx/models/nn_ref.py`
（**新文件**，不动 `nn.py`）。它们与 `nn` 的关键差别：`nn_v8` 的**打分**是 `z(lin)+z(top)`
逐日标准化 ⇒ 打分时必须拿到日边界（`ModelBase.predict_needs_day`）。

神经网络按**"日"分批**（`batch_days`）而不是按行 —— 逐日 softmax 与逐日 IC 都要当天的**完整**截面，
随机抽行会把不同天的股票混进同一个 softmax 分母，目标就废了。
