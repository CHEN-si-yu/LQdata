# 日频因子工程

每天在上游更新完成后运行：

```bash
python /root/autodl-fs/featureengineering/main.py
```

默认补齐至上游 `stock_daily` 的最后一个交易日，从任意工作目录运行均可。缺少依赖时入口自动使用共享环境 `/autodl-fs/data/miniconda3/bin/python`。上游仍在更新时会自动等待（支持绝对路径、相对路径和项目目录中的模块启动），最长 6 小时；另一个因子写入任务运行时拒绝并发写入。退出码 0 才表示本轮更新和台账核对完成。 必需上游数据集整体缺失时，在因子写入前明确失败；正常稀疏事件的空表与个别字段缺失仍按各因子口径处理。

## 单元边界与目录职责（硬约定，改代码前必读）

**本单元自成一体。** 它只做一件事：运行入口 `python main.py`，读上游 `../datadownload/data`，
把全部产物写在本目录内。**不读、不写、不依赖本目录之外的任何位置。**

### 目录职责

| 目录 | 职责 | 谁生成 |
|---|---|---|
| `data/factors/`、`data/market_factors/` | **最终产物**：因子与标签，按 `year=YYYY` 分区 | 引擎 |
| `data/derived/{intraday,chips,open5,market_morning}/` | **派生层预聚合缓存**：把超大原始表（5 分钟线 8.4 GB、筹码 6.24 亿行）压成日频宽表，供几十个因子共用 | 引擎按需 |
| `state/` | 台账：每因子一份 JSON（recipe 指纹 / coverage / 分区身份 / 输入水位）；另有 `state/runs/` 运行账本、`state/input_hashes/` 上游输入身份缓存 | 引擎 |
| `logs/` | `factors.log` 主运行日志、`backfill_<年>.log` 各年重建块日志 | 引擎 |
| `artifacts/` | `catalog/` 因子字典、`checks/` 体检输出、`pit/` 前视审计、`dayhash/` 逐日 MD5 台账、`audits/` 审计工作区 | 引擎与审计 |
| `conf/`、`factors/`、`fea/`、`scripts/`、`tests/` | 配置、因子定义、引擎、工具、测试 | 人 |

### 硬规则

1. **路径一律用 `cfg.root` 拼接，禁止 `cfg.root.parent`。** `parent` 是「项目的父目录」，
   等于把产物放到单元外面；项目一挪位置或换机器，东西就散到别处去了。
   新路径先加进 `conf/config.yaml` 的 `paths:`，再在 `fea/config.py` 暴露 property。
2. **禁止把任何产物写到本目录之外。** 缓存、日志、运行账本、因子字典、体检输出、
   审计报告 —— 全部在项目内。审计工作区放 `artifacts/audits/<日期>/`。
3. **禁止引用项目外的既有目录当作自己的存储。** 需要跨单元共享的只读输入，
   只能是通过 `conf/config.yaml` 声明的上游路径（当前只有 `../datadownload/data`）。
4. **审计不得碰生产台账。** 审计/沙箱用 `--sandbox <dir>` 与 `FEA_CACHE_DIR <dir>`
   把产物和缓存重定向出去，只读生产产物。（`Engine.prebuild` 在 recipe 变化时会把
   已清空的 manifest 落盘，没隔离就会把生产台账清掉 —— 实测踩过一次。）

### 为什么写这一节：CodeX 的教训（2026-09-25）

2026-09-24 的审计把本模块的运行产物逐步挪到了项目外的 `/autodl-fs/data/CodeX/`：
派生层缓存、主日志、运行账本、因子字典、体检输出、前视报告、输入哈希。其中派生层那次
还用了 `os.link` **硬链接**把旧数据链过去 —— 于是同一份数据有两处目录项（同一 inode，
`du` 也算不准），并且补丁只改了父类、漏了 `MarketLayer` 的同名覆写，两处路径逻辑各写各的。
到 2026-09-25，CodeX 已积累 32 GB、14000 余个文件，其中还混着多轮审计的硬链接备份；
`README` 里五处把 CodeX 当证据引用，读代码时很难分清「哪个是本模块的运行产物、哪个是历史归档」。

代价是具体的：以为在清缓存，其实删的是另一份硬链接；以为在看生产日志，其实看的是审计副本。
**运行产物和历史归档混在一个外部目录里，两件事都会做错。**

所以现在：运行产物一律在项目内；历史审计归档不放在这里，也不被这里引用。
`CodeX` 目录已整体删除，本模块对它零依赖。

## 时间轴对齐（硬约定，加新因子必读）

**每个因子的分区都必须从 `default_start`（2018-01-01）起，一年不缺。** 下游按因子拼
`[T, C]` 矩阵时列必须是齐的，参差不齐的起点无法直接喂进模型。

`FactorSpec.start` 的语义因此是「**从哪天起有真实值**」，**不再是**「从哪天起有分区」——
起点之前的年份（**对齐区间**）同样产出分区，布局与正常年份完全一致
（同 4 列 / 同 dtype / 同股票轴 / 同 `year=YYYY` 路径），只是值由 `align_fill` 决定：

| `align_fill` | 含义 | 何时用 |
|---|---|---|
| `nan`（**默认**） | 填 NaN | 上游**根本没有**这段数据，保持「不知道」。典型：涨跌停族依赖的 `stock_limit_list` 上游最早只有 2020-01-02 |
| `0.0` | 填 0 | 上游对这段区间**有明确口径**（如财报字段未披露时恒为精确 0.0）。填 0 是与上游口径一致，**不是**凭空断言 |
| `None` | 关掉对齐（逃生舱） | 极少数确需参差起点的场合 |

**对齐区间的 rank 恒为 NaN** —— 常量列的截面百分位没有意义，写个数字会被下游当成真实区分度。

⚠️ **填 0 是有代价的**：它断言一个并不存在的观测（"2018 年该股涨停 0 次"）。
**只有在上游确实以 0 表达"无"时才可以填 0**；上游缺表 / 缺序列 / 缺字段一律用 NaN。
判据必须是**实测** —— 读上游那一年的那一列、看精确 0 的占比，不能靠注释或推断。

### 加新因子时的检查清单

1. 新因子若声明了晚于 `default_start` 的 `start`，**必须**同时确定 `align_fill`，
   并写清依据（哪个上游表 / 哪个字段 / 哪一年的实测）。
2. **优先放开起点真算**：若实测显示上游在早年份**有真实值**（非零占比可观），
   就该去掉 `start` 让它算，**而不是**填 0 —— 填 0 会覆盖掉真实观测。
   （2026-09-25 实测：`fin_exp_int_exp` 在 2018 年有 44% 真实值、`rd_exp` 49%、
   `fin_exp_int_inc` 50% —— 这 3 个因子原本被截断在 2019-05-01，现已放开。）
3. 加完跑 `python main.py check`，确认日期轴从 2018-01-02 起完整。

### 一条必须记住的规律（2026-09-25 的教训）

> **每引入一个新契约字段，必须把「会删 / 会改 / 会重建数据」的旁路工具全部过一遍。**

`align_fill` 引入时漏了四处，各自都是一个真缺陷：

- `fea/history.py` 的裁剪下界仍用真实起点 ⇒ 会把这些**对齐分区整年删掉**
  （实测枚举 **35 个分区 / 18 个因子**），而 `main.py rebuild` 成功后**无条件调用它**
  ⇒ 下一轮重建即引爆。**已修**（`cutoff_of`）。
- `scripts/rebuild_manifest.py` 重建台账时丢了 `file_identity` ⇒ 「分区被外部改动」
  的自愈检测被静默关闭（账有盘坏）。**已修**。
- **两处校验器不认识契约**，把合法的填充分区当成缺陷恒久报错（"狼来了"会淹没真回归）：
  `scripts/backfill_history.py::_scan_thin`（报「整年全 NaN＝垃圾分区」）与
  `fea/validation.py`（报「市场有效日值缺失 N 天」，实测 7 个 `mkt_limit_*` 各报 2 条）。
  **已修**：两处都按 `resolved_start` 跳过对齐区间。

**一句话总结这条规律**：新契约字段不只要改「生产路径」，还要改**所有读它、
判它、删它、重建它的旁路** —— 删数据的（history）、重建台账的（rebuild_manifest）、
判定合规的（validation / _scan_thin），一处漏掉就是一个静默缺陷。

## 数据范围与可用时点

- 输出下界为 2018-01-01，第一个交易日是 2018-01-02；历史输入继续用于预热。
  **所有因子的分区都从这一天起对齐**（见上一节）；晚起点因子的早年份是对齐填充，
  各自的确切起点见因子字典的 `start` 列。
- 股票池使用 `conf/universe_frozen.tsv` 的 **2115 只固定主板股票**：名单冻结时存续、2016-08-09 起未出现 ST、上市不晚于 2018-01-01。该选择包含幸存者偏差和事后筛选，不能解释为当年可投资全市场。
- 普通因子在 T 日收盘后、依赖到齐后生成，供 T+1 使用。融资融券等滞后数据按实际可得日移位；公告按公告日及现行披露契约对齐。上游不保存的历史发布版本无法由因子工程还原。
- 财务历史状态从最早可用源分区读取，按公告时点选取当时最新版本，不因同批任务或预热长度改变。长披露空档可能沿用非常陈旧的已知财报；厂商只保留较晚修订版本时，不能反推其原始披露值。
- 价格水平用原始价；收益用原始价与截至当时累计复权因子。禁止用未来日期的复权基准重写历史。
- 停牌与缺测有明确区分：真实成交要求 `vol>0`；状态价格可前向沿用，波动与成交统计排除缺测。缺失保持 NaN，禁止用未来值回填。
- 5 个标签用 T+1 开盘买入、T+1+h 开盘卖出，h 为 1/3/5/10/20。买卖日均须有真实成交；尚未成熟的尾部为 NaN，后续行情到齐后补齐。

行业相关因子采用历史收益相关性形成的行业代理，并非官方个股行业归属。候选指数只保留通达信 0 类中名称与东方财富明确标注“行业板块”精确匹配的子集，排除总市值、涨跌家数等统计序列；年度分组只使用该年之前的行情。名称不一致的真实行业会被排除，当前分类字典和厂商回填历史无法证明当年的实际发布版本。

★ 两批的**样本口径不同，名字里就带标记**：`mkt_full_*` = **全市场口径**
（`stock_market_distribution_history` 是上游按全市聚合好的家数，还原不到 2115 池）；
其余 = 固定池口径。两种口径的数值**不可直接比较**。

市场因子描述市场状态，尚未验证预测收益。指数类使用指数本身的官方编制范围；股票统计类只使用固定 2115 只股票中的有效样本，不把缺测计入分母，少于 100 个有效样本为 NaN。

上午数据要求 09:35 至 11:30 的 24 根完整 5 分钟棒，使用右端时间戳；上午成交额必须为正，零成交报价不计入有效样本。收益参考价为当日已知的前收盘价；只使用上午价量，不使用下午成交信息。**11:30 是指标截面时点，当前上游是日终供数，生产可用时间仍是收盘后。** 指数采用价格指数，收益没有再计入分红。 离散阈值比较使用 `1e-12 + 1e-12 × abs(基准)` 的数值容差：恰好 5% 计入“至少 5%”，恰好等于均线不计入“高于均线”，防止二进制舍入误判。

## 增量、重建与台账

默认回刷最近 **10 个日历日**（通常约 5–8 个交易日，节假日会变化），并自动修补缺口。文件内容 MD5、上游逐日台账、逻辑指纹或股票池变化可触发更早重算；**但自动回填的下界一律夹在尾部回刷窗内** —— 更早的输入变化只记录、不回填（见下）。父因子的修订传播至依赖它的后续输出。预热锚定输出年份，保证同一年全量与增量计算窗口一致。

### ★ 「历史不可变」：自动回填的下界（2026-09-29 契约变更）

**引擎自己的 as-of 口径是** `pit = max(ann_date, f_ann_date, end_date)`（`fea/deriv.py`：
"不按 ann_date 去重，而是保留所有版本，as-of 时取最新可见版本"）
⇒ **一条新公告对"它公告之前"的任何一天都不可见**，那些天的因子值**在数学上不可能变**。
所以"上游旧年分区变了就从那年年初中算到今天"是**纯空转**。

实测（2026-09-29）：厂商新增 225 行「报告期 2018–2024、`ann_date` 在 2026 年」的财务数据
⇒ 旧逻辑让 **217 个因子重算 2018–2025、约 28 分钟 CPU、窗口内逐格 0 变化**。

现在（`Engine._frozen_span`）：

| 回填路径 | 是否受冻结 |
|:--|:--|
| L1b 尾部回刷（`revision_days`） | **它就是冻结下界本身**（`freeze = rev`） |
| L2 `changed_days`（上游逐日台账） | ✅ 夹到冻结下界 |
| L2 `changed_files`（分区内容 md5、旧年） | ✅ 夹到冻结下界 |
| L2 `dep_backfill`（`dep_backfill_days`） | ✅ **2026-09-30 起改为内容驱动**（见下） |
| 显式 `--refresh` / `--rebuild` / `--start` | ❌ **不冻** —— 人工重建必须能回到任意历史 |
| L1a 分区文件缺失/身份不符 | ❌ 不冻"区间"，但**已覆盖的历史一律剔出**（见下） |

**被冻掉的部分不丢**：记进 `Engine.frozen_input_changes` → `report.json.frozen_input_changes`，
每条形如 `{factor, dep, source, earliest_changed, freeze_floor, frozen_days}`。
这是「厂商是否原地改写了历史值」的**唯一观测通道**（厂商替换数据无解，只能观测）。

**写盘守卫**（`store.upsert_year`，本轮为**观测层**）：写盘前把新内容与旧分区逐格比 ——
相同则**跳过写盘**（省 IO；且 mtime 不变 ⇒ 下次 plan 的 L1a 不会把"逐字节重写"误判成损坏）；
不同则照写，但差异摘要进 manifest 的 `partitions[y].last_write` →
`report.json.partition_rewrites` / `partition_rewrites_skipped`。
**本轮只记录不拦截**；观察确认历史项恒为 0 后再考虑升级为硬拦截。

#### ★★★ 2026-09-30：升级为**硬不变量**（用户拍板，因子工程的固有属性）

> 用户原话：「我们设计的因子就必须要有『**不能被未来数据增量更新而改变历史数据**』这个固有属性。
> 这一点是我们整个因子工程的核心逻辑，所以那个刷新历史数据的相关逻辑判断理论上就不能触发，
> 也没有存在的意义。我们只能通过观测台账、逻辑分析等判断历史数据是否要刷新。」

**契约**：日常增量运行（无 `--refresh` / `--rebuild` / `--start`）
**在结构上不可能重算"已覆盖"的历史** —— 不是在每条路径上判断该不该，而是
`plan()` 收尾**统一剔除**：凡「台账已覆盖」且「早于冻结下界 `end − revision_days`」的日期，
一律不进计划，只记进 `Engine.history_recompute` → `report.json.history_recompute`
（`{factor, year, days, earliest, latest, freeze_floor}`）。

「已覆盖」这个限定词不能丢 —— 两个方向都要保：

| 情形 | 处理 | 为什么 |
|:--|:--|:--|
| 已覆盖 + 冻结区之前 | **剔出计划** | 这才是"改历史"，引擎永远不替你做 |
| **未**覆盖（新因子的对齐分区、真空洞） | 放行 | 那是**创建**不是**改写**；否则新因子永远拿不到 2018 起的对齐布局 |

**同时把三条"会自动重算历史"的来源逐个消掉**（它们才是真凶，不是判断本身）：

| # | 来源 | 原行为 | 现行为 |
|:--|:--|:--|:--|
| 1 | **L1a 分区身份误判** | `[size, mtime_ns]` ≠ 台账 ⇒ 判"被外部改动" ⇒ **整年重建** | **先验内容再定损坏**：`_partition_matches_record()` 只读 Parquet footer，行数与日期上下界仍与台账一致 ⇒ **只刷新身份**（`identity_refreshed`）。2026-09-30 实测：正是它让 550 个因子的 `year=2026` 全被误判，99550 个任务里 **97% 逐格零变化**（② 从 ~7 min 涨到 12.1 min） |
| 2 | **对齐区间每年重写** | 26/24 个晚起点因子的 2018/2019 整年填充行，**每跑一次重写一次** | 分区**已就位就不再重写**（逐格恒同、纯空转） |

### 并行度（`--jobs`）

两段并行**不重叠**，都受同一个 `--jobs` 控制：

1. **派生层构建**（`Engine.prebuild`，因子 worker fork **之前**）。四个层互相独立 —— intraday / open5 / market_morning 读 `stock_history_5min`，chips 读 `stock_cyq_chips` —— 且各写各的 `data/derived/<层>/_manifest.json` 和自己的 year 分区，跨层**没有共享文件**，所以按层并行、不需要任何锁。没工作（`yr[1] < yr[0]`）的层不进计划，一个分区都不动。
   实测单层单年：`intraday 63s · chips 82s · open5 39s · market_morning 76s`；四层串行 260.5s → 并行 **81.6s（3.19×）**，已是层并行的理论上界（等于最慢的 chips）。已逐位核对：并行产物与串行产物 md5 完全相同。
2. **因子计算**（`Engine.run_parallel`），按 (因子, 年) 分派。

`--jobs` 上限由环境变量 **`FEA_MAX_JOBS`** 控制（默认 **12**）。提高前先用 `scripts/mem_trace.py` 实测。

#### 阶梯实测：最优是 12，不是越大越好（2026-09-25）

单年块（2018，513 因子，25 核 / 90 GB 容器），每档清空因子产物与台账后重跑：

| jobs | 墙钟 | 真实计费内存峰值 | 批内 RSS(诊断，虚高) | CPU |
|---|---|---|---|---|
| 4 | 350 s | 37.5 GB / 90 | 39.5 GB | 3.9 核 |
| 8 | 240 s | 45.4 GB / 90 | 46.3 GB | 7.9 核 |
| **12** | **205 s** | **52.2 GB / 90** | 52.8 GB | 11.8 核 |
| 16 | 215 s ⬅ **反而更慢** | 58.8 GB / 90 | 59.4 GB | 15.6 核 |

**曲线在 12 处拐弯。**原因是**共享盘 I/O 争用**：12 个进程同读同一批年分区，
再加进程只会互相排队。此时 CPU 只用到 11.8/25 核、内存离 90 GB 还有 38 GB ——
**瓶颈既不是核也不是内存**。所以默认上限取实测最优的 12，而不是"能用多少用多少"。

参考：`--jobs 1` 18.3 min/年 · `--jobs 2` 11.7 min/年。层并行那一段受层的个数限制
（最多 4 路），与 `--jobs` 再大也无关。

#### ★ 按年份并行（2026-09-29 实测）：**每年 `--jobs 3`、每批 3 年**

`scripts/backfill_history.py` 是**逐年串行**的（`--jobs` 只管**年内**并发）；
而 `main.py run`（非 slice-worker）会抢 `state/daily.lock` ⇒ 直接并行必然互挡。
**`main.py run --slice-worker` 不碰锁**（走的正是 `fea/daily.py` 给每年用的那条路）⇒ 按年并行可行。

**安全性依据**：年份之间写的是**不同的**因子年分区；相邻年份会重写**同一批**
`data/derived/<层>/year=YYYY` 分区，但那是 `store._atomic_write`（PID tmp + `os.replace`）
⇒ **原子、最后写入者胜出、内容确定**，不会撕裂。

实测（本机 12 核 / 90 GiB，2018–2020 三年 × 550 因子 × `--refresh`）：

| 配置 | 墙钟 | 峰值 anon | **计费峰值 / 90 GiB** | 结果 |
|:--|--:|--:|--:|:--|
| 3 年 × `--jobs 4`（12 worker） | 9.2 min | 83.77 GiB | **89.2（99.1%）** | ✘ **2020 那块崩**（`BrokenProcessPool`） |
| **3 年 × `--jobs 3`（9 worker）** | 11.2 min | 66.56 GiB | **73.91（82.1%）** | ✔ **3/3 全过** |

★ **`3 年 × jobs 4` 是危险档**：顶到 89.2/90 GiB，离炸只差 0.8 GiB。
★ cgroup 的 `oom_kill=0` / `failcnt=0`、宿主机 363 GiB 空闲 ⇒ **两层 OOM 都没触发**；
   最可能是撞到 `configure()` 给**每个进程**设的 **`RLIMIT_AS = 24 GiB`**。
   **`BrokenProcessPool` 是内存压力的表现，不是 MemoryError。**
★ 并行有效：3 年串行约 25 min → 并行 **11.2 min（约 2.2×）**。

##### ⚠️ 但 `--jobs 3` **也不是恒安全** —— 正式 9 年全量重构的实测（2026-09-29 深夜）

同一天做了 9 年（2018–2026）全量重构，每批 3 年 × `--jobs 3`，
**峰值贴得很近**，批与批之间会翻车（有些因子本身就吃内存）：

| 批次 | 各年计费峰值 / 90 GiB | 结果 |
|:--|:--|:--|
| 2018, 2019, 2020 | 77.98 / 77.60 / 77.98 | ✔ 3/3 |
| 2021, 2022, 2023 | **81.62 / 81.62** / 81.00 | ✘ **2021、2022 被 81.0 GiB 的护栏掐掉**（已跑约 95%）；2023 ✔ |
| 2024, 2025, 2026 | 80.76 / **81.46** / 80.75 | ✘ **2025 被掐掉**；2024、2026 ✔ |

⇒ **`--jobs 3` 的峰值落在 77.6~81.6 GiB 区间，紧贴 81.0 GiB 的护栏线，偶发翻车。**
**要稳，用 `--jobs 2`（或 2 年 × `jobs 3`）。** 护栏本身工作正常 —— 它保住了容器，
代价只是那一年要重跑。

★ **续跑很便宜**：被杀掉的年份**不带 `--refresh`** 重跑即可 —— `_finalize` 是**逐因子**
提交 coverage 的，所以 `plan()` 只会算缺失的那部分，不必整年重算。

**驱动器**：`check/incremental_20260929/year_parallel_rebuild.py`（会话产物，用
`fea.resources.run_bounded` 做内存护栏 —— 它超限时只 kill **自己那个进程组**，不误伤别的年份）。
若要固化成生产工具，应把 `--year-jobs` 加进 `scripts/backfill_history.py`。

#### 内存护栏：同一道闸，曾经两个方向都错

`fea/resources.py::run_bounded` 原来按「进程组内每个进程 `VmRSS` 求和 > 64 GB」
停批。实测两个方向都错，都已修（现在主判据是**容器真实计费内存 vs 真实上限**，
两者从 cgroup 动态读）：

- **触发太早（浪费）**：`VmRSS` 把 fork 共享的页**按进程各算一遍**，实测虚高 1.3~1.5×。
  按 64 GB 停批等于真实用量 ~44 GB 就掐断 —— **容器一半内存用不上**，直接压死并行度。
- **触发太晚（危险）**：另一道闸读 `total_rss` 当"匿名内存"，阈值写死 80 GB。
  但容器被计费的是 `total_rss + total_cache`：实测 `32.9 + 11.0 = 44.6 GB`，
  **漏看 11.7 GB**。按此推算真实用量要 ~91.7 GB 才触发 —— **会在护栏动作前先被内核 OOM**。
  本工作负载专读 6.86 亿行 / 6.24 亿行的 parquet，页缓存正是最大的一块波动量。

判据拆分后：主判据 `计费内存 > 上限×0.90`；第二道 `不可回收量 > 上限−14 GB`；
批内 VmRSS 求和**降级为诊断输出**（`peak_cgroup_bytes` 才是结论，别拿 `peak_rss_bytes` 下判断）。

#### 两条踩过的坑

- **`multiprocessing` 默认 start method 在 Python 3.14 已是 `forkserver`。** `_LAYER_WORK`
  与 `_WORKER_ENGINE` 两个模块级全局**只有真 `fork` 才可见** —— `mp_context=mp.get_context("fork")`
  是**承重结构**，删掉它层并行与因子并行会同时静默失效。（非 Linux 上 `get_context("fork")` 直接抛错。）
- **临时文件名不能是确定性的。** `_atomic_json` / `_atomic_write` 原来写 `path + ".tmp"`。
  `Upstream.watermark()` 是**写**操作、会被**每个 worker** 调用，而上游更新后的第一次 run
  会让所有 worker 同时 cache miss → N 个进程以 `"w"` 截断同一个 tmp →
  要么 `os.replace` 抛 `FileNotFoundError`（任务失败、整轮非零），要么留下被截断的 JSON
  （下次 `json.loads` 失败，静默退化成每次重算 md5）。**并行度越高越容易撞**。现已加 PID。

#### 并行度建议（按场景）

| 场景 | 建议 | 理由 |
|---|---|---|
| 全量重建（早年份） | `--jobs 12` | 峰值 ~55–74 GiB，安全 |
| 全量重建（2023 以后） | `--jobs 8` | 12 路会撞 81 GiB 护栏；8 路峰值 ~74–76 GiB |
| 日常增量 | `--jobs 8` | 实测 **169 s**（对比串行 ~12–13 min，约 4.5×），峰值 75.5 GiB |
| 派生层相位 | 固定 ≤4 | 只有 4 个层，天然上界；与 `--jobs` 再大无关 |

⚠️ **日更的并行度要单独想**：`main.py run` 不带参数时 `--jobs` 默认 0 → `safe_jobs` 归一为 **1（串行）**。
要提速必须显式 `--jobs N`。日更虽然任务少，但每个 worker 仍要装整层价格/派生缓存，
**峰值与跑一整年相当**（实测 75.5 GiB），所以不要因为"只算几天"就把并行度开很大。

## 数值环境与可复现性（2026-09-25）

因子落盘值的**末位**取决于浮点实现，不只是代码和输入。实测（2026-09-25）：

- numpy 的 **float32 超越函数**（`arcsinh`/`log1p`/`expm1`/`power` …）走 SIMD 核，
  与「双精度算完再舍入」在 **24.76%** 的输入上不一致（最多 2 ULP）；
  同一个函数在 **float64** 下与 libm **逐位相同（0.000%）**。
- 后果：同一份代码 + 同一份输入（逐文件 md5 核对）+ 同一个计算计划，
  只因为跑在另一套 numpy 上，**87 个对象**的历史值就在末位漂移；`main.py` 只能把它
  报成「无法解释的历史变化」并返回非零。实测漂移率 25.4% 与核差异率 24.76% 吻合。

因此（三条硬约定，改代码前先读）：

1. **入口无条件钉死共享解释器**（`main.py` 顶部）。以前只在当前解释器**缺 numpy** 时
   才切到 `/autodl-fs/data/miniconda3/bin/python` —— 而镜像里另有一套自带 numpy 的
   python，那种情况下会静默换掉浮点实现、且不留任何痕迹。
2. **数值环境指纹进 `recipe`**：numpy 版本 + 固定算例的位模式哈希
   （`fea/resources.py::numeric_env_fingerprint`）。换解释器 / 换 numpy **会**改变
   逻辑指纹 → 引擎按既有规则强制全量重建并在日志写明原因。
   ⚠️ 换环境后的第一次 `main.py` 因此会重建全部历史（本机约 3 小时）；这是有意的：
   宁可显式重建，也不让两套浮点实现的结果混在同一份产物里。
3. **数学在 float64 上做，只在落盘处压 float32**。禁止把 float32 数组（或 Series）送进
   超越函数。`ctx.safe_div` 以前返回 float32，调用方紧接着的 `np.arcsinh` 就走了
   float32 核（`factors/annual_field_expansion.py` 正是这个形态），现已改为返回 float64。

审计工具（**按实际执行取证**，比读源码可靠 —— 能覆盖 lambda、辅助函数和派生层）：

```bash
# 记录所有「float32 进超越函数」的调用点（不改任何数值）
FEA_FP_GUARD=/tmp/guard.jsonl python main.py run <因子...> --sandbox /tmp/x
# 环境不变性测试：把 numpy 的 float32 核换成另一套实现，输出必须逐位不变
python scripts/env_invariance_test.py out.json <因子...>
```

常驻回归见 `tests/test_numeric_reproducibility.py`（safe_div 的 dtype、指纹稳定性与
对 float32 核的敏感性、探针本身）。沙箱审计可用 `FEA_CACHE_DIR` 把派生层缓存
（chips/intraday/market_morning/open5）也隔离到独立目录，避免碰到生产缓存。

### 推荐技术路线

1. **先固定验收口径和输入。** 阅读数据侧最新说明与流水，确认股票池、有效起点、日线实际截止日、延迟源和公告时点；用实际日线水位决定结束日期，不能用延伸到未来的交易日历。保存代码、状态、因子文件备份及输入身份，计算前后检查输入是否变化。
2. **先审公式，再做小规模真实样本复现。** 对全部注册因子逐项记录源字段、单位、父因子、公式、有效分母、停牌和缺失处理、预热长度、输出格式及可用时点。动态记录实际读取的依赖，与声明逐项核对。优先检查单独/批量、短/长预热、跨年、阈值等边界，确认公共逻辑后再安排全量，减少发现公共问题后的重复重建。
3. **修复必须让受影响历史失效。** 数值逻辑改变后提升版本或公共逻辑指纹，重建受影响因子及其后代；不能只回刷最近几日。长窗口、嵌套窗口和递推指标要按输出年份固定计算锚点，防止全量与增量初始化不同。依赖拓扑和原计划应可恢复，失败不能被新的台账基线掩盖。
4. **将三类证据分开检查。** 全历史检查日期/股票轴、主键、类型、行数、状态、有限值和有效起点；原始数据独立复算检查公式；因果检查真正截断未来输入，再与生产 value、rank、NaN 位置精确比较。每个普通/市场因子都要选到有真实有效值的日期，晚起点因子另选截点；未来收益标签单独检查成熟和买卖日条件。
5. **实测全量、增量和破坏恢复。** 保存全量结果的最近日期片段及 MD5，执行正常无参数入口，逐日对账；标签覆盖更长成熟窗口。破坏测试先备份，实际删除最新几日并保留旧台账，检验受损识别与增量恢复；同时比较整段历史、父因子和语义台账，确认非测试区间没被改坏。另在隔离副本测试旧年源修订和跨年新增，不能修改生产原始数据来造测试。
6. **收尾应有明确停止条件。** 输入稳定、全部对象结构通过、有效样本因果比较通过、重复更新一致、删除恢复一致、历史修订与跨年追加通过、下一次计划合理后交付。旧结果与修复结果发生变化需要解释；同源复算意外变化必须解决。保留仍有效的既有证据，只重做被代码或输入变化影响的检查，避免通过后继续扩大探索。

### 本次暴露的关键问题与处理技巧

| 问题 | 审核与维护要点 |
|---|---|
| 财务结果随同批因子变化 | 财务状态要读取最早可用源分区中的已知历史，不能由本次预热长度决定。实际样本曾因较早已知财报被短窗口遗漏，导致单独与批量不同；应比较不同窗口、字段组合和批次，不能只做一次同批重复运行。 |
| 公告截断误判 | 实际财报按现行契约检查 ann_date、f_ann_date、end_date 的最大有效日期；已经公告的业绩预告可以描述未来报告期，不能因此删掉。审计脚本也要有回归样例，区分程序缺陷、审计方法错误和源数据历史版本缺失。 |
| 浮点边界与缺失分母 | 恰好 5% 或等于均线会受二进制舍入影响；离散比较须有明确容差与等号语义。用独立原始数据/十进制例子验证；零成交、缺测、无效报价不能计入有效样本。不可用未来值填补缺失来提高覆盖率。 |
| 分钟和行业数据口径 | 上午截面必须核对 24 根完整右端标记分钟棒、成交额单位及正成交条件；日终供数不能宣称盘中可用。行业候选需排除统计序列，年度映射只用此前收益；当前字典或固定池不构成历史成分证明。 |
| MD5、文件身份与台账混淆 | 逐日 MD5 使用规范化 float32、固定代码排序和统一 NaN；文件容器 MD5另行比较保存的日期片段。语义台账比较覆盖、逻辑指纹、行数及内容依赖，允许物理替换时间变化；物理文件身份仍用于识别受损和依赖更新，不能直接取消。 |
| 父因子重建与旧年回算 | 全历史重写父因子可能因文件身份变化保守触发后代回算，即使数值相同。完成后检查下一次计划，排除反复重算旧年的问题；正常跨年标签成熟或真实历史源修订需要回算，不能机械禁止。 |
| 资源和验收耗时 | 计算按年释放缓存，默认串行、数值库单线程，监测本任务进程合计 RSS，并遵守 90 GB 上限。独立只读检查可在受控内存下并行；年度文件读取和全历史比较也可能耗时，应报告具体阶段，而不能以“进程未报错”代替通过。 |
| **末位漂移：浮点实现也算输入**（2026-09-25） | 同一份代码 + 同一份输入 + 同一计划，换一套 numpy 就让 87 个对象的历史值在末位漂移。判据不是"读源码看有没有浮点"，而是**按实际执行取证**：`FEA_FP_GUARD` 记录所有「float32 进超越函数」的调用点；`env_invariance_test.py` 把 float32 核换成另一套实现，输出必须逐位不变。修法：钉死解释器 + 环境指纹进 recipe + 数学统一 float64。 |
| **审计脚本别碰生产状态**（2026-09-25） | `Engine.prebuild` 在 recipe 变化时会把"已清空的 manifest"落盘（引擎的有意行为）。审计/验证脚本若没隔离 `state/`，会直接把生产台账清空 —— 实测踩过一次。审计一律重定向 state 与 `FEA_CACHE_DIR`，只读产物、不写状态。 |

备份若采用硬链接，生产和测试必须通过原子替换写文件，禁止原地改写导致备份一起变化。**硬链接还会让「删除」变得违反直觉**：同一 inode 有多个目录项时，删掉一处并不会释放空间，`du` 也只在同一次遍历里去重（实测曾在 CodeX 里把 1.7 GB 的缓存读成 208 KB）。失败时恢复备份；已执行的破坏测试不要直接重跑并覆盖原基线。模板复制到 `artifacts/audits/<日期>/` 并更新日期与范围后再用。
