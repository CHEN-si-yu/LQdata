进入服务器后，首先系统理解当前项目的整体框架与上下游数据流，重点关注：

- 上游原始数据字段及其定义、频率、覆盖范围和可用性；
- 当前 `feature engineering` 的整体框架、因子生成流程、校验机制及正式因子库；
- 下游模型实际使用的数据范围，包括当前关注的股票池、时间范围、预测目标以及模型对因子的使用方式。

本次任务的核心目标是：**基于现有原始字段，持续研究、开发和验证新的有效因子，并逐步扩充高质量因子库。**

需要注意，本次工作不是简单地批量构造公式，而应将每一个新因子视为一个完整的研究任务。因子的起点应当首先是一个具有明确逻辑的 **Idea / Hypothesis**，然后结合现有数据字段进行定义、实现、实验和验证，最终决定是否进入正式因子体系。

### 1. 因子开发要求

所有新增因子必须严格对齐当前已有的因子工程框架，包括数据读取方式、计算接口、时间对齐规则、缓存机制、命名规范、校验流程以及正式入库方式等。原则上不要另起一套体系，而是在现有框架内部进行扩展。

因子至少需要满足以下基本要求：

- 不应大面积为空，具有足够的数据覆盖率；
- 不应为常数或近似常数；
- 应具备一定程度的预测信号，而不是纯随机噪声；
- 与已有因子相比应具有一定新增信息，避免大量生成高度重复或高度相关的因子；
- 严禁任何形式的未来信息泄露；
- 因子的历史值必须具有 **point-in-time** 一致性，即未来新增或变化的数据不能反向改变当时已经能够计算得到的历史因子值；
- 因子必须能够在当前实际股票池和实际模型时间范围内稳定计算，而不仅是在全量数据上的理论可计算；
- 对异常值、停牌、缺失值、上市时间不足等情况，应遵循当前因子工程已有的数据处理规范。

这些只是进入研究流程的**基本底线**，不能把通过上述检查直接等同于“有效因子”。

### 2. 采用“研究提出者—独立执行者—审核者”的开发机制

本次因子研究需要特别避免一个问题：

> **不能由同一个 Agent 同时提出假设、完成实验，再自行宣布实验成功。**

你在整个任务中主要承担 **研究负责人 / 裁判员 / Reviewer** 的角色。

推荐采用以下工作机制：

**第一步：提出研究方向**

你根据已有原始字段、金融逻辑、市场微观结构、统计规律以及当前已有因子的覆盖情况，提出一个明确的因子研究 Idea。

Idea 至少应说明：

- 想捕捉什么市场现象；
- 背后的经济或统计逻辑是什么；
- 需要使用哪些已有原始字段；
- 与当前已有因子相比，潜在新增信息是什么；
- 初步计划如何构造和验证。

**第二步：交给新的独立 Agent 执行**

针对每一个研究 Idea，尽可能启动一个新的 Agent，由其独立完成：

- 阅读相关数据和已有代码；
- 设计具体因子表达方式；
- 编写因子实现；
- 执行必要的数据质量检查；
- 完成因子统计分析和预测能力测试；
- 与已有因子进行相关性和重复性分析；
- 输出完整实验结果和研究结论。

不同 Idea 尽量交给不同的 Agent 独立研究，减少前序结论对后续实验的路径依赖。

**第三步：由你统一审核**

你不应直接接受执行 Agent 给出的“有效”“无效”等主观结论，而应依据实验数据重新审核。

重点判断：

- 因子逻辑是否成立；
- 是否存在未来数据泄露或时间对齐问题；
- 是否存在实现错误；
- 覆盖率是否足够；
- 信号是否稳定；
- 是否只在极少数年份、股票或特殊市场环境中有效；
- 是否与已有因子高度重复；
- 新增信息量是否足够；
- 是否值得进入正式因子库。

最终由你决定：

- **Accept**：进入正式因子库；
- **Revise**：修改后重新实验；
- **Reject**：终止该方向；
- **Extend**：当前结果有价值，进一步衍生新的研究方向。

也就是说，形成：

**Idea → Independent Agent Research → Experimental Evidence → Reviewer Audit → Accept / Revise / Reject / Extend**

这样的完整闭环，而不是简单地：

**写一个公式 → 跑一下结果 → 有 IC → 加入因子库。**

### 3. 持续探索新的研究方向

本次任务不是开发固定数量的因子后结束，而是需要持续进行研究迭代。

每完成一轮研究后，应结合：

- 已成功的因子；
- 已失败的因子；
- 已有因子的相关性结构；
- 当前原始字段仍未充分利用的信息；
- 下游模型当前的薄弱方向；

继续提出新的研究 Idea。

尤其需要关注**不同类型、不同逻辑来源的因子**，不要长期集中在同一种公式变换或同一类技术指标上。

失败实验同样需要保留研究记录。应明确记录失败原因，例如：

- 没有预测信号；
- 信号不稳定；
- 与已有因子高度重复；
- 覆盖率过低；
- 对异常数据敏感；
- 存在时间对齐问题；
- 计算成本过高而收益有限。

避免未来不同 Agent 重复尝试已经明确失败的方向。

### 4. 以实际下游任务作为最终评价环境

所有因子研究应围绕当前真实下游模型任务展开，而不是脱离实际任务单独评价因子。

当前只关注下游模型实际使用的：

- 指定股票范围；
- 指定时间范围；
- 实际预测目标。

因此，因子的统计性质和预测能力应优先在这一真实任务域中评估。

可以参考更大范围的数据进行辅助分析，但最终判断必须以当前下游任务对应的数据域为准。

### 5. 充分利用服务器计算资源

当前服务器资源：

- **CPU：32 核**
- **内存：60 GB**

服务器非常适合进行多 Agent、多因子以及多参数组合的并行实验，应充分利用并行计算能力，提高研究效率。

可以并行开展：

- 不同 Idea 的研究；
- 不同因子的计算；
- 横截面统计；
- IC / RankIC 等指标计算；
- 因子相关性分析；
- 不同时间窗口或参数组合实验。

但是必须严格控制内存占用。

**60 GB 是绝对上限，不允许超过。**

建议：

> **整体峰值内存尽量控制在 50 GB 以下。**

启动大规模并行任务前，应根据单任务内存占用估算合理并发数，避免简单按照 32 CPU 核全部并发，导致内存 OOM。

如果 CPU 与内存约束发生冲突：

> **优先保证内存安全，其次再追求 CPU 利用率。**

### 最终目标

最终目标不是单纯增加因子数量，而是逐步形成一套：

**有明确 Idea → 独立研究 → 严格实验 → 独立审核 → 正式入库 → 持续迭代**

的因子研究体系。

重点寻找真正能够为当前下游预测任务提供**新增、稳定、可复现预测信息**的因子，而不是机械地堆积大量公式型因子。
