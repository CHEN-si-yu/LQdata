# 因子侧一键更新交付说明（2026-10-06）

## 日常入口

在上游数据写入完成、其写入进程退出后，从项目根目录执行：

```bash
python main.py
```

无参数会走正式生产 `run`，对象范围由 `conf/production.json` 决定。生产入口从上游 `stock_daily` 的实际有效日期水位确定本轮截止日；它不把 `2026-09-30` 等研究快照日期当作永久截止值。入口会等待识别到的上游写入进程；等待结束后，如果上游还没有更新到预期的新交易日，它会按当时可见水位运行，因此调用者应先确认上游更新确实完成。

## 首次全量与后续增量

新获正式批准的因子由主审先完成研究生命周期审核，并加入 `conf/production.json`。候选登记、研究运行或一份建议报告都不会自动把因子加入生产。完成正式批准后，仍使用同一个命令 `python main.py`：

- 对没有正式输出覆盖的新对象，入口按声明的起点、预热和完整日期轴补齐至当前 `stock_daily` 水位；缺少必需上游表时会报错，不把空结果当成历史数据。
- 对已覆盖对象，入口根据源水位、文件身份、定义与 manifest 规划增量和允许的近期修订回刷；完好的既有历史覆盖会跳过。损坏或缺失的分区按恢复计划处理。
- 正式标签的尾部端点尚未成熟时保留缺失，后续上游数据到齐后由同一入口更新；不需要手工设置固定结束日。

完整无参数日更成功后，入口按配置自动运行质量监控、刷新机器因子字典并发布完整生产集合。以退出码 0、日志中的“发布完成”和更新后的 `state/current_release.json` 确认完成。指定因子、限制日期或沙箱运行属于限定任务，不等价于完整发布。

## 失败恢复

修复失败原因后，保留 `state/daily_inflight.json`、对应 `state/runs/` 记录、质量报告和日志，再执行同一条无参数命令：

```bash
python main.py
```

程序会恢复尚未完成的计划并核对原始输入身份。不要删除或手改 inflight、manifest、失败记录来制造“已完成”状态；不要为普通日更改用 `--start`、`--refresh` 或 `rebuild`。如果失败期间上游内容或代码身份发生变化，恢复逻辑可能要求重新核验相关历史。

## 全库检查的边界

`main.py status` 和 `main.py check` 的旧式遍历只覆盖 `factors/` 注册规格，不能据此判断所有由研究生命周期转入生产的对象都已覆盖。日常发布流程自带完整对象集的质量监控；发布后的检查应以当前 release、该次 `state/runs/<run_id>/report.json` 与 `quality.json` 为准。不要把 `status` 或 `check` 的无错误输出当成整库发布验收。
