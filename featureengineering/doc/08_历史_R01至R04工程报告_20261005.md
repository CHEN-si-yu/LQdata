### 本轮确立的方法学结论

**原始 RankIC 与分年同号不足以判定因子价值。** 三个反例：`supply_pressure_interaction`
（声明 +0.0320、9/9，但控制风格后 t*=-2.66 符号反向，是换手波动率代理，rho=0.856）、
`ex_days_since_w250`（+0.0197、9/9，t*=+1.48，是动量代理）、
`dividend_stability_w750`（+0.0121、9/9，t*=-0.58，与股息率 rho=0.876）。
而两个真正过关的原始 IC 只有 0.0082 与 0.0028。

**因此在原有 G1-G6 之外增加 G7 增量检验**：逐日截面 Fama-MacBeth 回归
`label_rank ~ [控制因子秩] + 候选秩`，控制 8 个通用风格因子
（`momentum_120` / `short_term_reversal_5` / `vol_120` / `idio_vol_60` / `log_mv` /
`turnover_std_20` / `bp` / `roe_ttm`），取候选系数的跨日 HAC t，
要求显著**且符号与登记方向一致**。用已生产因子定标：`s26_structure_side_hhi_v1` t=+12.21/+7.29，
`s26_liq_up_fragility_v1` t=-9.02/-8.28。

方法学演进：`相关性阈值` -> 发现不足 -> `残差 IC` -> 发现会被残差方差衰减、会误杀真因子
-> **`Fama-MacBeth 系数 + HAC t + 已入库因子定标`**。

### 两类新的伪发现模式（本轮首次量化）

1. **低两两相关、高联合解释力**：`free_float_rank_252` 与全库 491 个因子的 max|rho| 仅 0.183，
   但它每天有 34-42% 的股票恰好取 0、截面只有约 242 个不同取值；这种半离散阶梯变量
   可被多个连续风格因子的线性组合重建，加入控制后系数从 -0.0057 塌到 -2.7e-05。
   **只看 max|rho| 会漏掉这类重复。**
2. **"敏感性变体"可能是"前视变体"**：`pledge_level_lag5` 把发布滞后从 15 个交易日缩到 5 个，
   增量 t 从 +1.02 跳到 +2.52；但实测本地水位显示供应商发布滞后约 13 个交易日，
   故 5 日滞后使用了当时读不到的数据。执行单元事前已在 `availability` 写明该判据，数据正好落在其上，
   因此判 Reject。**审核敏感性变体必须检查其可用性假设。**

### 5.4 强制规则：方向翻转是流程性风险，不是个人疏忽

本轮 **Lead 与执行 Agent 各自独立犯了同一个错误**：拿**原始尺度**的 FM / 残差数字
去和**声明尺度**的 RankIC 比较，漏做 `higher_is_better` 翻转，
从而把一个"方向支持、增量偏弱"的候选误读成"符号反转的代理"。
（Lead 在本轮共犯两次同类错误：一次是分年同号缺符号条件，一次是漏做方向翻转。）

**因此立为强制规则**：
1. 任何增量类指标在解读前必须先过 `higher_is_better`（true: declared=raw；false: declared=−raw）。
   `evaluation.json` 的 `summary[].rankic` **已经是 declared 值**，不得当 raw 使用。
2. 报告里所有增量类指标（FM 系数与 t、残差 IC、正交后残差、分层收益）**必须 raw / declared 双列**；
   只报一列的报告不予审核通过。
3. 判定一律用 declared 列：一致为正 ≥ 7/9 年 → 方向得到支持；一致为负 → 被证伪；混杂 → 无稳定信号。

### 5.5 本轮新量化的伪发现模式

1. **低两两相关、高联合解释力**：`free_float_rank_252` 与全库 491 个因子的 max\|rho\| 仅 **0.183**，
   但每天有 34–42% 的股票恰好取 0、截面只有约 243 个不同取值；这种半离散阶梯变量可被多个连续风格因子的
   **线性组合**重建，加入控制后系数从 −0.0057 塌到 −2.7e-05。**只看 max\|rho\| 会漏掉这类重复。**
2. **敏感性变体其实是前视变体**：某候选把发布滞后从 15 个交易日缩到 5 个，增量 t 从 +1.02 跳到 +2.52；
   但实测本地水位显示供应商发布滞后约 13 个交易日，5 日滞后使用了当时读不到的数据。
   **审核敏感性变体必须检查其可用性假设，而不只是看数字。**
3. **同一 Idea 下两个机制可能是同一轴的正反写法**：`rv_skewness` 与 `signed_jump` 的日截面 rho = **−0.9582**，
   却被同向登记为 `true` ⇒ 必有一错（实测一端 9/9 成立、另一端 0/9 被证伪）。
   **机制集合必须在预登记阶段做两两相关性预判**；高度共线时只登记一端，或明确写成"同一轴的正反检验"。

### 5.6 基础设施教训（两起事故 + 一次 Lead 判断失误）

1. **inode 耗尽**：`/autodl-fs/data` 是 AutoFS，**总 inode 仅 200,000**（空间还有 101 GB）。
   本工程每跑一个研究候选会创建私有 phase 派生缓存（约 100–140 个 inode），两轮消耗约 4 万个后打满，
   **全队无法创建任何文件**（连 `failure.json` 都写不下）。处置：只清理可再生/零证据价值的对象
   （`__pycache__`、无 `run.json` 的孤儿 run、历史快照），未删任何有 evaluation/verification 的 run。
   **结构性建议：为本工程产物单列存储，或调大该挂载的 inode 上限。**
2. **交付目录被并行会话删除**：`dsh_scratch/round2` 与 `round3` 在 06:53 被本队之外的活动整棵删除。
   底层证据（`artifacts/research/` 下的 runs/evaluations/verifications）**从未丢失**，未重跑任何计算。
   处置：改为**三处落地**（服务器交付目录 + 容器本地 `/tmp/r3safe/` + 本机镜像），
   并禁止任何 Agent 对共享交付目录做递归删除。**该共享盘存在并行会话互相干扰的风险。**
3. **资源护栏必须用不可回收量**：Lead 曾按 `memory.current`（80 GiB）拉响内存警报并让一个 Agent kill 了
   正在跑 40 分钟的 run；事后分解发现 `anon`（不可回收）只有 **51.8 GiB**，其余 25 GiB 是可回收页缓存，
   `oom_kill` 始终为 0。**教训：护栏用 `memory.stat: anon`，不要用 `memory.current`。**
4. **被 kill 的 run 会留下 `begin.json` 但没有 `run.json`**：若工具按"目录存在"判定完成，
   会把残缺 run 当成已完成并**直接拿半成品去 evaluate**，静默产出错误结论。
5. **`fea/resources.py` 对每个计算进程强制 `RLIMIT_AS = 24 GiB`，且无环境变量可覆盖**（提高须改 `conf/config.yaml`）。
   R3-C 的筹码形态候选在 `research verify` 的截断阶段抛 `ArrayMemoryError: Unable to allocate 1013 MiB`，
   根因就是这一条：verify 的三个阶段在同一进程内累积虚拟地址空间，而 `stock_cyq_chips` 的派生层读取需要更多。
   结果是 **R3-C 五个候选 verify 0/5 通过** —— 卡点是框架级资源限制，不是候选实现。
   该限制同样会影响任何依赖大内存读取的族（如分钟线）。**待办：让 `RLIMIT_AS` 可按进程/按族显式声明。**
   **修法：只在 `run.json` 存在时才算完成。**
