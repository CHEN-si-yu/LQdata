## 1. 项目事实（核验后按实际为准）

- 项目根 `/autodl-fs/data/featureengineering`；上游原始数据只读；所有产物在项目内。
- 生产入口 `python main.py`（增量）；研究入口 `python scripts/research_cli.py`（idea/family/candidate/run/evaluate/verify/promote）。
- 落盘合同：股票因子/标签 `data/factors/<name>/year=YYYY/data.parquet`（四列 trade_date/stock_code/value/rank，float32，rank 口径沿用 Engine）；市场因子两列（trade_date/value）。计算 float64 落盘 float32；完整键轴、NaN 保留、原子写入，不自行改格式。
- 注册来源：`conf/production.json`（status=production）+ `artifacts/research/catalog/candidates/<id>.json` 的冻结定义；清单以 `main.py list` 为准，**不引用历史文档的数量**。
- 计数口径：正式股票因子（不含市场对象与标签）。R16 收尾基线：**260 个正式股票因子**（另有 47 个市场对象、5 个标签，合计 312；以注册表实际为准）。R17 目标：股票因子总数 >500；R17 于 2026-10-19 按用户指示收尾，最终为 **310 个正式股票因子**（另有 47 个市场对象、5 个标签，合计 362；新增 50，未达 500）。后续轮次若获授权，以 310 为新的开工基线。
- 初始股票池为带幸存者选择的冻结池（2115 只）；结论只针对该池。

## 2. 因子开发的基本要求（底线，不等于有效）

- 覆盖足够、非常数、非纯噪声；与现库有新增信息；严禁未来信息；历史值 PIT 一致（未来数据不能反向改写历史值）。
- 对齐现有框架（Context/Engine/Store 计算与落盘、声明直接输入与父依赖、warmup_days 为日历天且锚点固定在输出年）；不另起体系。
- 数据时点红线：财务按公告可得日、报告期只用于 TTM/单季/同比；价格收益端点必须真实成交（`traded[d-1]&traded[d]`，跨停牌恢复收益要显式检查）；分钟源有单位切换史（2025-12-01 前后手→股）必须按基础层实际逻辑核验；月末只能用已完成且日历确认的月份。
- 零值三分：缺失 / 未披露 / 经济真实零值分开；没有依据不填零。

## 3. 「提出者—独立执行者—主审」机制（核心纪律）

**不能由同一个 Agent 自提 Idea、自跑实验、自宣成功。** 主 Agent（你）担任主审/裁判，子 Agent（≤用户允许的并发上限）担任独立研究员。

闭环：**Idea → 冻结定义（含公式/参数/方向/来源/门槛/SHA）→ 独立子 Agent 研究 → 实验证据 → 主审独立核验 → Accept / Revise / Reject / Extend →（Accept 时）晋级生产**。

主审不直接采信子 Agent 的「有效/无效」结论，逐项重算或读原始证据再裁决。历史上多个提案在「主审重读数据」后被推翻（如近互补、互补腿、家族补控消除增量），这条纪律是产出质量的主要来源。

## 4. 资源纪律（2026-10-08 沉淀，硬约束）

- 容器硬限 60 GiB（64,424,509,440 字节）；用户要求更严格的 60e9 字节控制；数值任务预算 55–57 GiB，守卫在预算 90%（约 51.3 GiB）自卫终止**所属任务组**。
- **charged 内存约 30 GB 是可回收 file cache**（并发读盘累积；容器无 drop_caches 权限）——kill 多由缓存累积触发而非真实计算内存。据此：全部重任务经 `bounded.py` 排队（聚合预留 ≤36GB；heavy(reserve≥8GB) 并发 ≤1–2、总并发 ≤4–6、heavy 按 queued_at FIFO 防饥饿；启动前重任务人工门 `memory.current` < 38GB、轻任务免门）。
- 数值线程=1；单任务 `--jobs` ≤2（分钟派生系 jobs=1）；同席同时最多 1 个重任务。
- 内存/磁盘/inode 预算：内存 <60 GiB、磁盘与 inode 共享 200GB/200k（启动任务前保留 25GB+20k inode）。CPU 优先让位于内存安全；以 50% 平均 CPU 利用率作为效率目标而非硬指标。
- 服务器只有本工程在工作；仍不得触碰 `/autodl-fs/data/` 下其它目录（dsh_scratch、model、tmp、datadownload 等）。

## 5. 人员编排（主审 + 子席位）

- 主 Agent = 主审：审设计、看初筛、跑/批释放（chief_release + 批量驱动）、维护台账与文档、控制资源与队列。**子 Agent 不修改生产注册、不改 `fea/*.py`/`research/*.py` 共享核心、不调用 promote、不跑 main.py（生产物化由主审侧统一做）**。
- 子席位数逐渐拉到用户上限（R15 为 5），每席一个主题：日频价格/路径、财务（报表结构与创新）、现金流/利润表、分钟微观结构、事件约束、跨股票网络/扩散。席位一律先读 SKILL+本文件+现行政策+methods。
- 子 Agent 只交付研究证据（SKILL §8 字段：方向/公式/机制/最接近现库/来源与可得日/覆盖与非常数/IC 与 HAC/两核增量/补控/全库 G5/run·eval·verify ID 与逐值对拍/路径与 SHA/资源/失败与下一步），汇报给主审，由主审裁决。

## 6. 流水线（每个候选的固定步骤）

1. **设计与冻结**：写 idea/family/candidate 平面 JSON（公式、参数预算、事前方向、来源表列与可得日、warmup、最近邻、家族补控、可证伪条件），登记入 Catalog，保存真实 candidate_id。冻结必须先于查看收益结果。
2. **纯 builder**：`research/families/<name>.py`，经 Context 声明输入与父依赖；先做合成反例/小样本对拍，再全轴。改公式必须换新版本、保留旧代码与旧证据。
3. **全轴构建**：2123 评价日（2018-01-02..2026-09-30）× 2115 股票 float32 数组。
4. **初筛** `round<N>/screen_v4.py`（C 通道出 G4/G7 的 v4 与 v3 双判定；GC 只判质量）。
5. **全库相关** `g5_current.py` / `r17_g5_batch.py`（R17 开工以 260 个现库对象为基线，收尾为 310；每次新因子入库后由 `library_cache_refresh.py` 扩充；旧报告用 `g5_extend.py` 扩展）。
6. **正式工程**：`research_cli.py run`（--jobs≤2）→ `formal_compare.py`（要求 different_cells=0，逐格定位任何差异）→ `formal_evidence.py`（真实输入截断 cutoff=2025-12-31 + 两阶段增量，逐格 float32 value/rank/NaN 一致）。
7. **主审裁决**：读证据核门槛 → 写 verdict（`chief_release.py` 逐项断言）→ `qualified→shadow→production` → `main.py run <name>` 物化 → `production_compare.py` 逐值+字节对拍 → 台账与文档。
8. 家族批用 `r15_batch_release.py`（verdict→extend→release→物化→库刷新→对拍）批处理。

## 7. 准入门槛（政策 v4/v4.1 摘要；裁决时读全文）

- C 通道（预测）：G2 全期 ≥20% 日 ≥100 股（<30% 标 sparse）；G3 在 ≥100 股截面 ≥90% 非常数；G4 声明方向 h1 或 h5 的日度 RankIC HAC 双侧 80% 下界>0 且 ≥4 正年；G5 对当前全部股票因子平均日度绝对 Spearman ≤0.95（>0.85 解释）；G7 BASE8 两核（rank/model）正系数正 t，强 t≥1.00、弱 t≥0.25，强核 ≥4 正年、各 ≥3 正年。C 一律标 weak_evidence=true；仅按 v4 放宽通过者标 relaxed_admission；弱核 t<0.50 等标 weak_increment。
- GC 通道（事前声明的经济/价格描述用途，无预测门槛）：≥100 股截面 ≥95% 非常数；G5 <0.98（0.95–0.98 专项审查）；估计不稳定/不可识别不通过。
- BASE8：momentum_120, short_term_reversal_5, vol_120, idio_vol_60, log_mv, turnover_std_20, bp, roe_ttm。
- 结构去重：排序同构/代数恒等/相反写法/同机制邻近窗口不计新因子；互补腿（和为 1 的池内份额）每池至多计 2 个；家族补控与最近邻必须真实进入联合回归，消除/反转增量者不入库（PRR vs momentum_20 案例）。

## 8. 历轮教训速查（写新设计前必读）

- **端点**：收益类必查真实成交端点（P007/P009/P011 的 304 格审计源于端点缺陷，v2 修复后才准入）。
- **累积序**：正式 run 的逐年 worker 面板与单轴面板会差 ≤48 ulp（P014 832 格、PRR 3 格）——对拍必须 0 差异，按 worker 面板重建而不是容忍。
- **互补与近互补**：份额池第三腿是恒等衍生；与现库 |ρ|>0.95（C）/0.98（GC）排除，0.95–0.98 专项审（leg_correlation 0.9716 拒）；主审要求的「经济最近邻+家族补控联合两核」是识别伪增量的决定性实验。
- **单位/口径**：财务单位对账（错 1000 倍会改样本）；简单比率单位相消也不跳过对账；IS03 类带符号指标必须披露负值语义与尾部。
- **内存**：kill 会烧掉 2–4h 长任务，宁可排队不要抢跑；heavy FIFO + 人工门 + jobs≤2 是三次事故后的收敛配置。
- **台账**：失败也留证（run ID、SHA、原因、修复链）；bounded 的 `<id>.log` 由它自建，勿重定向同名；JOB_ID 全馆唯一。
- 更多案例见 `02_研究_设计方法与案例.md` 与 `doc/04_研究记录_R15交付_20261008.md` §四。
