## 〇、一句话结论

> **`rebuild` 的 `--factors` 不是"只算这些因子"的开关，`--resume` 才是跳过开关；
> 而 31 个新因子补 6 个不完整年份时，**两者都救不了重复计算** ——

## 一、★★ 最重要的一条：**别再做全量重算**

### 故障现场
```bash
# 我执行的（错误）
python main.py rebuild --jobs 6 --streams 1        # 无 --factors，无 --resume
```
### 实际后果（实测）
```
年块调度：9 普通块 · 1 路 × 3 车道
[启动] 2018 · **209 项** · jobs=3      ← 每年都派发全部 209 项
[完成] 2018 · 8.8 min · 峰值 48.2 GiB
[启动] 2019 · 209 项
[完成] 2019 · 8.7 min · 峰值 51.6 GiB
...
⇒ 9 年 × 8.7 分钟 ≈ **78 分钟**，而真正缺数据的只有 31 个因子的 6 个年份
```

### 根因（代码证据）
```python
# main.py:669
rb.add_argument("--resume", action="store_true",
                help="跳过已验收完成的年；默认强制重算")
# main.py:809
rc = run_rebuild(cfg_rb, specs=specs, y_from=y_from, y_to=y_to,
                 force=not args.resume,      # ★ 关键：不加 --resume ⇒ force=True
                 jobs=..., streams=..., budget_bytes=..., dry_run=...)
```
**⇒ 不加 `--resume` 时 `force=True` ⇒ 强制重算所有年份。**

**且即使加了 `--resume` 也救不了**：跳过判据是**整年完整性**，不是因子：
```python
# fea/engine.py:1090
#   `backfill._year_done` 都要求日期轴从 `align_start` 起完整。
```
**⇒ 只要该年有任何因子不完整，整年就要重算 —— 而我需要补的 6 个年份全都不完整。**

### 三层跳过机制（必须区分清楚）

| 层级 | 机制 | 粒度 | 效果 |
|---|---|---|---|
| **写盘层** | `store._content_identical` | **因子 × 年** | 算完发现与已有文件逐格相同 ⇒ **跳过写盘**（日志："跳过写盘 176 个"） |
| **年份层** | `--resume` / `force=not resume` | **整年** | 该年日期轴完整 ⇒ 整年跳过 |
| **因子层** | **不存在自动跳过** | — | **每年一律派发全部因子** |

**★ 关键区分：跳过写盘 ≠ 跳过计算。**
写盘层省的是磁盘 I/O，**CPU 已经花掉了** —— 实测 `[启动] 20XX · 209 项` 就是证据。

### ⇒ 正确用法（写进 SOP）

| 场景 | 正确命令 | 说明 |
|---|---|---|
| **只补若干新因子** | `rebuild --factors <名单> ...` | 缩小因子集合（**注意：实测年块仍报 209 项，未能真正收窄，须进一步验证**） |
| **断点续跑** | `rebuild --resume --jobs N` | 跳过**已完整**的年 |
| **日常增量** | `python main.py`（无参数） | 自动只补缺失部分 —— **默认应优先用它** |
| **全量重算** | `rebuild --adaptive` | **仅在换季/上游变更时使用，并明确接受全量成本** |

**★ 铁律**：
> **在 `rebuild` 之前，必须先问："哪些因子缺？缺哪些年？那些年是否完整？"**
> **若只是少数因子缺少数年份 ⇒ 优先用 `main.py run <因子名>`（增量），而不是 `rebuild`。**

## 二、★ `research verify` 的真实成本（准入的硬门槛）

### 实测数据
| 观测 | 数值 |
|---|---|
| 单条全区间 verify | **1,420s / 1,793s / 2,385s**（23.7 / 29.9 / 39.8 分钟） |
| 对照：主 run 耗时 | 24 分钟 |
| **⇒ 准入一个因子 ≈ 两次全区间计算** | — |

**且 verify 是 CPU 密集单线程**（实测 `cputime/elapsed ≈ 0.96`），**`--jobs` 基本无效**。

### 并发调优实测
| 并发数 | 结果 |
|---|---|
| **3–4 条** | 单条 30–35 分钟，每核效率 **96%** |
| **7 条** | 单条被拉长到 **~55 分钟**（争用） |
| **21 条** | CPU 从 12.5% → **65%**（20.8/32 核），单条效率仍 **94%** ⇒ **推荐 15–20 条** |

**★ 结论**：verify 可安全高并发（内存每条约 1.1 GB），**15–20 条是甜点区**。

## 三、★ 入库链路（三级晋升，不可跳级）

```python
# research/catalog.py
STATES      = ("candidate","qualified","shadow","production","paused","retired")
TRANSITIONS = candidate → {qualified, retired}
              qualified → {shadow, paused, retired}
              shadow    → {production, paused, retired}
              production→ {paused, retired}
```
### 硬性前置条件（实测报错原文）
```
# research/lifecycle.py:62
ValueError: Qualification requires actual evaluation and full/incremental/causal verification IDs
```
**⇒ `promote --to qualified` 必须同时提供 `--evaluation` 与 `--verification`，
且两者必须同源（`verification.reference_run == evaluation.calculation_run_id`）。**

### 正确链路
```bash
python main.py research verify <run_id> --cutoff 20241231 --jobs 3
python main.py research promote <cid> --to qualified  --reason "..." --evaluation <e> --verification <v>
python main.py research promote <cid> --to shadow     --reason "..." --evaluation <e> --verification <v>
python main.py research promote <cid> --to production --reason "..." --evaluation <e> --verification <v>
python main.py docs                       # 刷新 artifacts/catalog
python main.py rebuild --factors <cid>    # 生成数据
```

## 四、★ 本次作业中我犯的 7 个操作错误（含症状与修复）

| # | 错误 | 症状 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | **停编排器未处理其在等的批次** | 4 条 verify 跑完但未晋升，`done` 为空 | 停 `pipeline.sh` 时它正 `wait` 子进程 | 从 verification 的 `reference_run` 反查并串行补跑晋升 |
| 2 | **晋升步骤并发撞 catalog 锁** | `BlockingIOError: [Errno 11] Resource temporarily unavailable` | 3 个 worker 同时 `promote` 争 `.candidate_registration.lock` | **verify 并行 + 晋升串行**（整段晋升用 `flock -x` 包住） |
| 3 | **批量式 lane-pool 有空转** | 3 条 verify `elapsed` 完全相同（同刻启动） | 用 `wait` 同步批次，批次间 CPU 空转 | 改**真 worker-pool**（`flock` 原子领取，谁先完成谁接下一单） |
| 4 | **重置 `gc_claimed` 导致记录丢失** | 17 条在飞任务的 claim 被清空 | 重建队列时重置了领取记录 | 用 `ps` 扫描在跑的 run_id 反推，不依赖 claim 文件 |
| 5 | **`drop_caches` 探测误报"可写"** | 内存治理器每 20 秒徒劳写一次 | 探测脚本用 `&&` 串联被截断，误判 | 实测 `Permission denied`，**停掉治理器** |
| 6 | **查错目录：把市场因子判为"未生成"** | 报"47 个尚未开始" | 市场因子存在 `data/market_factors/`，不在 `data/factors/` | 分类型核对存储位置 |
| 7 | **用生造术语"面板生成"** | 用户无法理解 | 术语习惯 | **一律用"因子的每日数值 / 数据文件"** |

## 五、★ 资源与护栏（实测口径）

| 项 | 值 | 说明 |
|---|---|---|
| CPU | **32 核**（`cpu.max = 3200000/100000`） | — |
| 容器内存硬限 | **60.0 GiB**（`memory.max = 64424509440`） | — |
| **项目护栏（rebuild 自报）** | `charged` **54.0 GiB** / `anon` **46.0 GiB** | 框架自动降档阈值 |
| 实测最严重峰值 | **charged 59.51 GiB（硬限的 99.2%）** | 由一个 8.78 GB 的"单年"run 造成 |
| **正确护栏指标** | **`grep '^anon ' /sys/fs/cgroup/memory.stat`** | `AGENTS.md` §E.1 明文 |
| **不要用** | `memory.current` | 含可回收页缓存（实测 41 GB 里 27 GB 是缓存） |
| 压力判据 | `memory.pressure avg10`（0.00 = 无压力） | — |

**★ 关于"55 GB 上限"**：**这个数字不是容器硬限，也不是用户设定的** ——
它来自我在会话早期自写的粗粒度策略，后来被我主动撤回。
**真实约束是 charged 54.0 GiB（项目护栏）与 memory.max 60 GiB（容器硬限）。**

### 单年块内存峰值实测（rebuild）
```
2018 年块：峰值 48.2 GiB
2019 年块：峰值 51.6 GiB
⇒ 距离 54.0 GiB 护栏仅 2.4 GiB ⇒ 框架自动把并发从 6 降到 3 车道
⇒ 32 核里只用 2.7 核 ⇒ **瓶颈是单因子内存占用，不是 CPU 或 I/O**
```

## 七、★ 一条必须遵守的作业前检查清单

**在启动任何 `rebuild` 之前，逐条确认：**

```
□ 1. 到底缺什么？     —— 逐因子核对 data/factors/<name>/year=* 的年份数
□ 2. 缺的年份完整吗？ —— 若某年日期轴完整 ⇒ 该年可被 --resume 跳过
□ 3. 能否用增量？     —— 少数因子缺少数年份 ⇒ 用 `main.py run <name>`，不用 rebuild
□ 4. 必须 rebuild 吗？—— 只有"多个年份不完整"或"上游变更"才需要
□ 5. 加 --resume 了吗？—— 不加就是 force=True，全量重算
□ 6. 内存预算够吗？   —— 单年块峰值已达 51.6 GiB，护栏 54.0 GiB
□ 7. 市场因子在哪？   —— data/market_factors/（不是 data/factors/）
```
