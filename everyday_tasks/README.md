## 备份清理与内存控制（2026-09-19）

日常仍只需运行 `main.py`，不会自动创建整库备份。手动入口现在也默认采用已验收的资源配置：3 个工作线程、最多 2 个在途请求、数值库 2 线程、进程地址空间上限 24 GiB；配置位于 `conf/daily.yaml` 的 `resources` 和 `api`。地址空间上限不是预分配内存，也不是显存；超过预算会报错，不能声称任务已成功。

`python main.py cleanup-backups` 预览可清理体积；加 `--apply` 执行。该操作与日更共用单实例锁，先按 8 MiB 块读取备份并持久保存每个文件的 MD5 和 SHA-256，之后只删除已经校验且未发生变化的数据副本。范围限于 `state/backtest/` 的 Parquet/数据归档/接口录制响应，以及已验证完成的 `datadownload/state/cyq_perf_full/` 分段副本。正式数据、共享 manifest、分钟 dump 原始缓存、代码备份、报告、原有单日 MD5 台账不删除。

校验清单保存在 `state/backtest/checksum_archives/`。**MD5/SHA-256 只能校验，不能恢复备份文件。** 清理后测试副本需要从正式数据或供应商重新构建；完成的全量下载检查点被清理后，重跑全量脚本会重新下载相应区间，日常增量不受影响。

### 后续维护原则

1. **日常从统一入口启动。** 手动运行 `main.py` 即可进入当前 32 接口的维护流程，不依赖 Agent；全量首次建库使用专用全量脚本。每次运行仍应检查最终报告及待处理告警，进程退出不等于所有接口成功。
2. **以上游响应和实盘为准。** HTTP 成功、返回空或本地水位推进均不能单独证明数据完整；分页必须结束、预期行数必须核对，持久状态必须晚于成功写盘。失败窗口要保留，不能为消除告警而跳过验证。
3. **将破坏性测试限定在隔离副本。** 新测试优先选择必要的日期、年度或实体，覆盖本地缺日、供应商新增、分页中断、写盘失败和重复执行，避免每轮复制整库。测试结束后先保存结果及校验清单，再通过 `main.py cleanup-backups` 预览、加 `--apply` 清理。
4. **校验清单不能代替恢复备份。** MD5/SHA-256 能用于内容核对，无法重建已删除文件。清理完成的全量下载分段后，重跑专用全量脚本会重新下载相应区间，日常增量不受影响；灾难恢复仍需独立备份或供应商重建能力。
5. **控制内存峰值要同时约束并发和读入粒度。** 校验按 8 MiB 块读取，避免一次载入整个大文件；下载并发不宜仅按 CPU 数增大。24 GiB 地址空间预算超限应报错，不能伪装成功。资源配置见 `conf/daily.yaml` 的 `resources`、`api`。
6. **历史缺口检测有范围。** 保留 coverage、没有失败记录且位于回看窗口外的历史缺行，不能保证所有接口自动发现。本地 MD5 抽查只能与本地台账比较，不能证明供应商未修订历史；需要时使用项目已有删日工具同步调整覆盖状态，或进行针对性的历史重取。
7. **下载正确不等于横截面回测无前视。** 财报需考虑公告日和真实可得时点，快照不能当作历史股票池；`winner_rate` 的真实返回可为 `85.11`，目前原值入库，不擅自按文档小数示例转换。发布时刻和单位仍需后续观测。

**待观察问题：** ST 接口在本次真实查询中返回空，客户端已保留历史并告警、重试，未证明上游恢复。默认闸门可能等待至超时，再按 partial 策略处理其他接口。后续检查报告，不应禁用该表或伪造成功来抹去告警。

| 退出码 | 含义 |
|:--|:--|

|:--|:--|:--|

| `✅ …；K 条需要关注` | 有告警 | 逐条按 §4 判读 |

## 2. 一轮做什么

### 2.1 六阶段

```
① 更新交易日历（到未来 T+30，供闸门回推 expected）
② 确定 T：问服务端"最新真正发布出来的交易日是哪天"
③ 闸门：检查各表在 T（或 T-delay）那天到齐没有；没到齐每 5 分钟重查，最长 6 小时
④ 先更新基础名单，再跑 18 张日频表
⑤ 跑其余表（分钟 / 季频 / 不定期 / 快照）
⑥ 单日 MD5 台账：重算尾部窗口指纹 + 抽查历史日（dayhash.sample_old_days，默认 3）
```

跑完输出 ASCII 汇总表 + `state/last_report.json`。

### 2.2 T / delay / 尾部窗口（三个核心概念）

**T = 服务端已发布的最新交易日**，不是"今天"。做法：从日历里今天及以前的最后 5 个交易日
**从新到旧**逐个问 `/stock/daily` 的行数，第一个达到"近 5 日中位数 × 70%"的就是 T；
再用 `/stock/adj_factor` 独立交叉验证。这样能自动处理"收盘前跑"和"半量发布"两种情况。

**delay = 有些表天生比 T 晚**。窗口上界一律收到 **`T - delay`**，不去够 T。

> ★ 现行唯一非零值是 **`stock_margin_detail = 1`**，其余全部 `0`（含 `dc_daily` /
> `stock_st_info` / `index_ths_daily` —— 它们是**发布晚**，不是**次日才有**）。
> **`registry._DELAY` 是唯一真源**，本文件若与它冲突以它为准。

**尾部窗口 = 最重要的自愈机制**：每张表**每轮无条件重抓**最近 `redundancy_days`（默认 5）
个交易日，不看任何标记。三个历史顽疾靠这一条同时解决：上游偶发返回空 / 服务端追溯修正 /
数据被误删。

### 2.3 闸门三档（`gate_tables()` 27 张）

| 档 | 成员 | 判据 | 行为 |
|:--|:--|:--|:--|
| **wait 等待** | **21 张** = 18 张日频 + `tdx_minute` + `stock_market_distribution_history` + `stock_history_5min` | 服务端在 `T-delay` 有数据 | **阻塞**（等到齐或超预算） |
| **watch 观测** | **7 张** = 4 张季频财报（`stock_income` / `stock_balancesheet` / `stock_cashflow` / `stock_financial_indicator`）+ `stock_forecast` + `stock_holder_number` + `stock_pledge_stat` | 探服务端最近有数据的一格 | **不阻塞**；落后时标 ⚠️ |
| **skip 跳过** | **4 张**无日历轴（`basic_calendar` / `stock_list` / `dc_blocks` / `tdx_blocks`） | — | 不参与 |

**为什么 watch 档不能阻塞（死锁论证，别改回去）**：闸门在跑批**之前**跑，服务端随时在发数据
⇒ 跑批前"本地 < 服务端"是**常态**；唯一能追平的办法就是跑批，而跑批正被闸门挡着。

**超时行为** `partial`（默认）：只跳过"没到齐的日频表"，非日频表照常跑。
`strict`：超时就不跑。要看是哪几张没到齐 → `$PY main.py gate --max-wait 0`。
某张表**连续几天**都到不齐 → 它的 delay 声明偏小 → §7。

**`_KNOWN_HOLES`（已知厂商洞白名单）**：期望日期正好落在洞里的表不再阻塞闸门（标 `⏭`、
报告降为 `ℹ️`）。**不等于放弃那天** —— 尾部窗口每天照常重试，上游一补发就自动抓回。
新发现厂商洞往 `registry._KNOWN_HOLES` 加日期即可（只加日期，不动 delay）。

### 2.4 六种抓取策略（按接口的"天然形状"选）

| 形状 | 含义 | 策略 |
|:--|:--|:--|
| **date 轴** | 能按时间段拿全市场，不用传股票代码 | 天然适合增量：只请求新增那几天。**成本随天数增长，与股票数无关** |
| **entity 轴** | 必须传实体代码、返回该实体全历史 | 天然适合全量刷新（且必须批量编组） |

| 模式 | 表数 | 怎么抓 | 例 |
|:--|--:|:--|:--|
| `range` | 11 | 按 `[区间]` 请求；区间 = 尾部窗口 ∪ coverage 缺口 ∪ revision 回刷窗口 | `stock_daily`（**1 个请求**拿全市场 6 天） |
| `per_date` | 6 | 一个交易日一个请求 | `dc_daily`、`stock_top_list` |
| `per_stock` | 5 | 四张财报表**只传报告期**就返回全市场（3 个请求），不用逐股；**另加 `ann_date` 日历日扫描兜底**（见 §9.11） | `stock_income` |
| `per_entity` | 5 | 按实体编组批量请求；已完成实体只补尾部窗口，未完成实体按年/月回填 | `stock_cyq_chips` |
| `snapshot` | 4 | 无日期轴，按周期全量刷新 | `stock_list`（每天）、`dc_blocks` / `tdx_blocks`（每 7 天） |
| `dump` | 1 | `daily_dump` 一次请求拿全市场当日 5min；**本地有按日缓存就先读缓存** | `stock_history_5min`（1 个请求顶 5901 个；命中缓存时 **0 个**） |

**按接口能力选策略的典型**：`/stock/daily` 不传代码就是全市场按日返回（1 请求 5500 行）；
`/stock/income` 只传 `end_date` 就返回全市场 6300 行（3 请求而不是 5901 个）；
`/tdx/daily` 传 `trade_date` 一次返回 1119 个板块。

### 2.5 耗时基线（T=2026-09-14 实测，39 张表 / 364 请求 / 409.4 s）

阶段分布：日历 1.0 s / 闸门 1.7 s / 日频 112.3 s / 其他频率 249.1 s / MD5 台账 45.2 s。

| 大头的表 | 耗时 | 请求 | 说明 |
|:--|--:|--:|:--|
| `stock_cyq_chips` | 74.7 s | 142 | 3 交易日窗口 × 3484 只，批量 100；请求翻倍是**有意**换自愈纵深（2→4 个交易日） |
| `tdx_minute` | 27.7 s | 19 | 618 板块，批量 100 |
| `stock_history_5min` | 22.1 s | **0** | 数据完整时只做完整性扫描，不重复下载 |
| `stock_financial_indicator` | 18.6 s | 3 | 3 个报告期**并发** |
| `stock_pledge_stat` | 16.4 s | 16 | revision 400 天回刷 |
| `stock_daily` | 8.4 s | 4 | 1 个请求拿全市场一天 |

**判断标准**：某表突然比基线慢 2 倍以上 → 查（看窗口/分页有没有失控）。

## 3. 水位、自愈与写盘

### 3.1 覆盖标记（coverage / done）

每张表在 `datadownload/state/<数据集>.json` 里记着：

- `coverage`：**已确认"这段没有缺口"的区间**（`run_range` 用它反推缺口）；
- `done.dates` / `done.entities` / `done.dumps`：逐日 / 逐实体 / 逐 dump 的完成标记。

> **★ 铁律：失败绝不标 coverage。** 一个区间只要有一个分片请求失败，整段就不标覆盖，
> 下一轮重新当缺口补。反过来，某个分片**成功但返回 0 行**（合法为空，比如非交易日），
> 那一片才标覆盖。

尾部窗口是无条件重抓的，所以即使 coverage 被误标，最近 5 个交易日也能自愈；
更早的日期靠 `coverage` 缺口 + `revision` 回刷窗口（逐表配置，低频表可到 400 天）。

**人工修复某一天**：
```bash
$PY main.py delete-day --date 2026-09-01   # 删除并自动备份，同时裁掉 coverage
$PY main.py run --no-wait                  # 下一轮就会把它当缺口补回来
```
（`--keep-coverage` 保留标记，用来检验"不看标记、只靠尾部窗口能不能自愈"。）

### 3.2 写盘（唯一路径 `store.upsert()`）

```
读旧分区 → 列对齐 → concat → 按主键去重（新数据赢）→ 稳定排序 → 写 .tmp → 原子替换
```

- **原子替换**：任何时刻断电都不会留下半个文件；
- **读不出来 ≠ 空表**：分区文件存在但读失败（网络盘抖动）→ **直接报错**，
  绝不当作"没有旧数据"去覆盖（那会把整个年分区抹掉）；
- **顺序铁律：先落数据、再落状态**。反过来会留下"状态说完成、数据还在内存"的永久空洞。

### 3.3 `daily_dump` 的按日缓存

`stock_history_5min` 有**两份**数据：

| 位置 | 是什么 | 谁在用 |
|:--|:--|:--|
| `data/stock_history_5min/year=YYYY/data.parquet` | 正式表（8 列，已过白名单 + 单位换算） | 因子工程 |
| `data/stock_daily_dump/date=YYYY-MM-DD/{data.parquet,meta.json}` | **原始件**（时间未过滤、单位未换算） | 本工程自己 |

每天补 5min 时**先读缓存**：那天在缓存里且是**完整交易日** → **0 请求 0 配额**直接用。
所以"删掉某一天再补回"是**零请求**的。原始件不加工的好处：将来改白名单判据或重标定 vol 单位
**不用重抓**（dump 配额是每个数据日期每天 10 次，重抓要按天排队）。

- 完整性判据 `cache_is_final`：bar 覆盖率 ≥98% **且** 行数 ≥ 0.9×"正常一天"。两道都要过 ——
  只靠覆盖率会漏判"只有一半股票、但每只都齐 48 根"的半份数据（实测）；
- 修复扫描窗口 `dump.repair_lookback_days` = **45 天**（接口本身能取最近 ~90 天）；
- 配额台账按**日历日**分桶、按**实际 HTTP 次数**计数（一次调用最多重试 5 次 = 6 个请求）；
  查看/清理 `$PY main.py dump-quota [--reset <日期|all>]`。

## 4. 告警判读与处置

### 4.1 等级表

| 等级 | 含义 | 计入 `rc=1`？ |
|:--|:--|:--|
| `✅` | 正常 | 否 |
| `ℹ️` | 记录性：上游撤数、已知厂商洞、厂商晚间重算 | **否**（2026-09-17 起） |
| `⏭` | 已知厂商洞（`_KNOWN_HOLES`） | 否 |
| `⚠️` | 部分失败 / 本地确实落后 | **是** |
| `🔴` | 单日 MD5 与台账不符 | **是** |
| `✘` | 失败 | **是** |
| `❓` | 闸门探测失败（不阻塞，但也没确认到齐） | 否 |

> `rc=1` 只表示"有要处理的告警"；记录性的 `ℹ️` 不再影响退出码 —— 否则一次几十条 ℹ️ 会让
> "数据一行没丢的一轮"被判成失败，watchdog 与 `&&` 链全部误判。报告里另有
> `alerts_actionable` 字段（机器读这个）。

### 4.2 三种告警怎么读

| 告警长相 | 真伪 | 处理 |
|:--|:--|:--|
| `⚠️ X 部分失败（未完成，下轮应自动重试）` | 真问题，但**会自愈** | 看是不是同一张表连着几天出现；连续出现 → 查上游或调策略 |
| `⚠️ X 本轮新增 0 行，且本地只到 A（应到 B）` | **真问题**：本地确实落后 | 记下来，第二天重点看有没有跟上 |
| `🔴 X <日期> 的单日 MD5 与台账不符` | 上游改了历史，**或**我们自己补全了数据 | **先看行数**（见下） |

> 「新增 0 行」**本身不是告警**。同一天跑第二遍、数据本来就在，就是 0 行。
> 只有"本地水位 < 它该到的日期"时才报 —— 所以**看到这条就是真的落后了**。

**🔴 的三种成因（按行数分）**：

| 现象 | 成因 | 处理 |
|:--|:--|:--|
| 行数**不变**，只有值变 | **厂商晚间重算定型**（实测 `stock_daily` 的 `stock_name` 改名、`index_daily`、`tdx_daily`） | 记录即可，**本轮跑批已自动对齐到服务端当前值** |
| 行数**变多** | **我们自己**用回刷窗口补的（实测 `stock_holder_number` 09-10 273→449） | 正常 |
| 行数**变少** / `（本地整天数据消失）` | 上游撤数，**或**我们这边那天的数据没了 | **要查**（§4.3） |

> ★ 实测结论：`stock_daily` / `stock_finance` 的 `stock_name` 回溯改名是**厂商的持续行为**，
> 09-10 ~ 09-17 每天都报；逐行比对服务端**0 条不同**。别当 bug 查。
>
> ★ 停牌股会**连带影响多张表**：同一天在 `stock_daily`（少 4 行）、`stock_history_5min`
> （少 96 根 bar）上同时表现为"少/变" —— 是同一件事，不是多个 bug。

### 4.3 急救命令

```bash
$PY main.py run --no-wait --force              # 卡住了 / 想强行再跑一轮
$PY main.py run --no-wait --only stock_cyq_chips   # 单表重跑
$PY main.py run --dry-run                      # 只打印计划、零写入（闸门只探一轮，不会等 6 小时）
$PY main.py backtest verify                    # 出现"疑似变少"时逐表比对指纹
ls -la state/backtest/deleted_*__<日期>.parquet # 看删除备份里有没有这天的原始行
$PY main.py hash-audit [--deep]                # MD5 台账自检（deep 要读数据，慢）
```

**永远不要在数据目录里手工 `rm` parquet。** 要修就用 `delete-day`（自动备份 + 裁 coverage），
或从 `state/backtest/full_<时间戳>/` 的硬链接快照回滚。

## 5. ★ 名单机制（2026-09-19 新增）

### 5.1 为什么要有

`index_ths_daily` 的抓取对象原来是**快照表** `index_ths_sector_categories`（厂商只存"当前"）。
该快照 2026-09-19 被删（快照对回溯训练必然前视），名单**固化**成静态文件
**`conf/ths_index_codes.txt`（1,676 只）**，改走 `DS.entity_codes`。

**这不是权宜之计**：名单原会随快照漂移（实测 2026-03-02 多 763 只、2026-09-14 少 291 只的
R/B 变体），每次都让 `index_ths_daily` 出现覆盖台阶，且新增实体的更早历史**永远补不齐**。
固化后覆盖范围固定、可复现，名单变化变成一件**要人做**的事。

> ⚠️ 两个 loader（新旧工程各一处）在名单文件缺失/为空时**大声报错**，不返回空清单 ——
> 空清单会让一个指数都不抓、而报告照旧 ✔（静默停更）。两边读**同一个文件**。

### 5.2 两件事已并进 `main.py`（用户要求：只跑 main.py 就能更新数据）

| 时机 | 动作 | 成本 | 失败影响 |
|:--|:--|:--|:--|
| **主体之前** | `roster.sync()`：问厂商 THS 名单，**新增的自动追加**进 `conf/ths_index_codes.txt` | 1 请求 | 只记一条 note，不中断 |
| **主体之后** | `roster.sweep_if_due()`：距上次 ≥ **30 天**才做全历史刷新兜底 | 约 40 请求 / 10 分钟 | 当日增量已入库，不受影响 |

**为什么 `sync` 必须在主体之前**：新增的代码不在 `done.entities` 里，`run_per_entity` 会走
`todo_new` 路径给它**全量回填历史**（不是只抓当天）。放主体之后就得白等一天。

`sync` 的三条安全约束：**空返回不当作"厂商清空了名单"**（否则会把名单误删成空 → 静默停更）；
**只增不减**；单次新增 > 200 只在报告里显著提示。

### 5.3 为什么不 sweep 就会留下永久的洞（结构性风险）

`strategies.py` 把实体分两类：

```python
todo_new = [c for c in codes if not man.is_done("entities", c)]   # → 全量回填
rest     = [c for c in codes if c not in set(todo_new)]           # → 只补尾部窗口（约 6 个交易日）
```

- ✅ **厂商新上的代码会自动全量回填** —— 只要加进名单，下一轮就走 `todo_new` 拉全历史；
- ⚠️ **已在 `done.entities` 里的实体只补尾部窗口**，**更早的洞永远不会自愈**。
  实测：480 只"从 2026-03-02 才有数据"的代码**全部**在 `done.entities` 里，洞从 3 月留到 9 月。
  表级 `_anchor_lo` 也救不了 —— 它锚的是表级 `max_partition_date()`，表整体不落后就不触发。

⇒ **对策**：定期跑 sweep（已自动，30 天一次），**每次往名单里加代码之后立刻跑一次**。
手动入口：`$PY main.py run --sweep-now`，或 `$PY scripts/backfill_index_ths_daily.py`（薄封装，
实现与线上同一份）。状态写在 `state/roster_sweep.json`。

### 5.4 名单维护与已知真相

- **厂商新上的指数不会自动进来**（这是拿"覆盖可复现"换来的取舍）。`scripts/check_ths_roster.py`
  把"厂商有新的"变成一件要人做的事：问一次 `/index/ths_sector_categories` 与固化名单 diff，
  报新增/消失；`--update` 可把新增追加进名单（只追加、不重排）。**只查不存**。
- **名单历史的深度参差是厂商侧的，不是我们丢的**：1,676 只里只有 3.5%（58 只）能回到 2010，
  29.7%（497 只）从 2026 才开始。按起始年份分档各抽 3 只向厂商求证，**更早的全部返回空**。
- **名单对研究窗的实际可用量**（完整覆盖 ≥98% 交易日）：

  | 窗口 | 交易日 | 有数据 | 完整覆盖 |
  |:--|--:|--:|--:|
  | test 窗 2025-09-01~2026-09-01 | 243 | 1,665 | 1,109 |
  | 近 1 年 train 2024-09-01~2025-08-10 | 226 | 1,176 | 1,153 |
  | 长 train 2020-01-01~2025-08-10 | 1,358 | 1,179 | **536** |

  ⇒ **要用长历史，可用池只有约 536 只**；只用近 1~2 年则有 1,100+ 只。这个约束是硬的。
- 名单里**最后日期落后**的 87 只（抽样 4 只向厂商求证）：**厂商的结束日期和我们完全一致**
  ⇒ 都是**厂商停供**，不是漏抓、也补不了。留在名单里的代价只是每次多一个空响应，
  好处是**厂商哪天恢复供应能自动发现**。

## 6. 单日 MD5 台账（发现"上游偷改历史"）

每轮增量之后，对尾部窗口内每个"数据集 × 日"重算一次**逻辑指纹**（行数 + 逐列值的哈希，
不是文件字节 —— 文件字节会因压缩/分块变化而**必然假红**），与 `state/dayhash/<表>.parquet` 比：

- 一致 → 什么都不做；不一致 → 报告里 `🔴` 定位到**数据集 / 日期 / 变化的列 / 行数变化**。

**历史那部分怎么保护**：尾部窗口只有 ~6 个交易日，更早的历史靠 `dayhash.sample_old_days`
（默认 3）**每轮从台账已有的日期里确定性轮换抽查**。想抽查更早的 → 先补台账：
`$PY main.py init-hashes --only <表>`（已**分批**，不会撑爆内存）。
台账本身健不健康 → `$PY main.py hash-audit [--deep]`。

## 7. delay 标定（主线任务）

> 用户原话：「很多东西只能在动态更新的时候才能发现，比如说 delay 到底是多少。
> 我需要连续跟踪几天才能够完全确认目前的配置。」

### 7.1 怎么看

`main.py monitor` 每晚做两件事：① 对每张有日历轴的表，从 T 往回逐个交易日问服务端
"这天有数据吗"，第一个"有"的就是它的服务端最新日期（稀疏表改用 10 天窗口一次问出来）；
② append 一条到 `state/monitor/history.jsonl`。

```
  Delay 标定追踪
  数据集                          声明          观测滞后(新→旧)   建议  稳  说明
  stock_margin_detail              1        1,1,1,1,1        1   ✔  与声明一致
```

- **稳**：`✔` 观测完全一致（可以定下来）· `⚡` 有起伏（T 当天时有时无）· `·` 样本不够；
- **⚡ 波动时取最大的那个滞后**（用户口径：「以稳定存在的为主……不要去冒险提取最新的数据」）。
  程序已经这样做：**取数窗口上界也是 `T - delay`**。

> ### ⚠️ `★改` 建议会误报 —— 先看采样时间
> 「标定追踪」读的是 `history.jsonl`，即**白天每一次采样**。很多表的毛病只是**发布晚**：
> 当天 18:11 / 21:01 / 21:22 采样都是滞后 1，**23:32 采样变 0** → 同一天里既有 0 又有 1，
> 表上就显示 `⚡` + `★改`。2026-09-15 深夜这一版把 **6 张表**误报成"应改 1"。
>
> **判据：把"跑批时刻（~22:00）之前"的采样丢掉再看**；或直接看闸门真正用的
> `state/delay_history.json`（每 T 只留一条、由跑批时写入，**不受白天采样污染**）。
> 月频/季频表会被报成 `★改 → 54` 这类荒唐值 —— 低频表在日频标定里的必然误报，**忽略**。
>
> ★ **2026-09-17 用户质询后的复核（纠正了当晚 agent 的错误判断）**：用户指出
> 「`stock_margin_detail` 的 delay **一定是 1**」。复核 11 次采样，2 次 `滞后=2`
> （09-15 18:11 / 21:01）**全部发生在服务端当天发布之前**；闸门真正用的
> `delay_history.json` 连续 3 天给出 `delay_obs=1` ⇒ **用户口径正确**。
> 另：monitor 的判据「0/11 次看到 T 当日就有数据」对 `delay=1` 的表**本就不适用**。

### 7.2 怎么定、怎么改

| 情况 | 结论 |
|:--|:--|
| 连续 **3 天**观测完全一致 | 可以定这个 delay |
| 有起伏（如 `1,0,1,1,0`） | **取最大值**（保守，只上不下） |
| 声明值 > 实测最大值 | 声明偏保守，可以下调，但建议先连续观察 5 天 |

工具只在 ≥3 天样本时才给建议。改 `data_incremental/registry.py` 的 **`_DELAY`**：

```python
_DELAY = {
    "stock_margin_detail": 1,   # ★ 用户 2026-09-15 拍板「一定是 1」：让闸门等它，别收窗口
    # 其余全部为 0（未列出的即 0）
}
```

> **⚠️ `_DELAY` 是唯一真源**，本文件可能滞后，改完顺手对一遍。
> `stock_st_info` / `index_ths_daily` 的**内联初值**仍在 `_reg`（`delay_days=1`），
> `_DELAY` 是覆写层，**改 delay 一律改 `_DELAY`**。

**改完必须验证**：`$PY main.py gate --max-wait 0` 确认闸门判据跟着变了，
再 `$PY main.py run --dry-run --no-wait --only <表名>` 看窗口上界是不是变成了 `T-delay`。

程序自己也有兜底：某张表**连续 3 轮**在该到的日期探测不到，自动按 `delay+1` 处理
（`delay.absent_streak`），**封顶 = 声明值 +2**（`gate.delay_autobump_max`，到顶打一条要人看的
告警）。但它只影响闸门判据、不改配置文件 —— **观察到的结论还是要人工写回 registry**。

## 8. ★★ 铁律与坑清单

### 8.1 权限铁律（2026-09-15 实际踩到，代价很大）

**本工程必须始终以同一个用户运行**（推荐统一用 `claude`）。
当晚一个 **root** 进程跑了 `main.py`，把 36 个 manifest 写成 `0600 root:root`，
而白天的任务以 `claude` 跑 —— **claude 读不到**。旧版 `Manifest.load` 把"读不出来"**静默当成
空 manifest**，再保存就把真实的 `coverage / done / columns` **覆盖成空** → `_missing_ranges`
认为"2010 年至今全是缺口" → 请求风暴 + 状态永久丢失。

已修两层：写入端所有落盘自动 `chmod 0664`；读取端遇到读不出**直接抛错**并打印修复命令。

**每晚开工前 30 秒自检**：
```bash
# 有输出 = 有文件当前用户读不了，必须先修
find /autodl-fs/data/datadownload/state -name '*.json' ! -readable -printf '%u %m %p\n'
# 一键修复（claude 在 root 组里，所以 g+rw 两边都能用）
sudo chgrp -R root /autodl-fs/data/datadownload/state /autodl-fs/data/datadownload/data
sudo chmod -R g+rw  /autodl-fs/data/datadownload/state /autodl-fs/data/datadownload/data
```

### 8.2 其它铁律

| # | 铁律 | 为什么 |
|:--|:--|:--|
| 1 | **禁止在数据目录手工 `rm` parquet** | 只有 `store.upsert()` 一条写盘路径；要删用 `delete-day`（自动备份 + 裁 coverage） |
| 2 | **`registry._DELAY` 是 delay 的唯一真源** | 文档会滞后；改 delay 一律改 `_DELAY`（内联 `delay_days=` 只是初值） |
| 3 | **不要改 `_DELAY` 去迎合 monitor 的 `★改`** | monitor 读的是白天采样，**已知误报**（见 §7.1）；闸门用的是 `delay_history.json` |
| 4 | **失败绝不标 coverage** | 标了就是永久空洞（旧工程 `index_daily` 缺 159 天的根因） |
| 5 | **先落数据、再落状态** | 反过来会留"状态说完成、数据还在内存"的永久空洞 |
| 6 | **`--sample` 之类收窄股票池的回测会被闸门挡** | 价格层按引擎代码轴落格，池子不同会**静默错位**（见 `model/README/SPEC.md` §3 末） |
| 7 | **不要用 `pkill -f "main.py"`** | 会匹配到自己那条命令行而自杀；用 `ps -eo pid,args \| grep '[m]ain\.py'` 找 PID |

### 8.3 ★ 修过的坑（2026-09-15 破坏性回测揪出的 14 个，**别再犯回去**）

判据都是"删掉一天能不能原样补回"。前 5 个会**静默毁数据**，最值得记住：

| # | 坑 | 后果 |
|:--|:--|:--|
| 1 | `store.read_parquet` 把"读失败"当"空表" | 网络盘一次瞬时读失败 → `upsert` 认为没有旧数据 → **整个年分区被这一天的增量覆盖**，且报告显示 ✔ |
| 2 | 拿 `max_partition_date()` 当"这天完成了" | 09-14 只有 2,304 行（正常 266,400）却让水位停在 09-14 → **9 GB 的表永久停在残缺口上** |
| 3 | 用 `done.dumps` 过滤候选日 | 某天成功 dump 过一次后，再删它就**永远**不再补 |
| 4 | `run_range` 在失败分片之后仍无条件 `add_coverage(a,b)` | 一个分片撞 502 → 整个区间被标"已覆盖" → **永久空洞** |
| 5 | `ctx.rev_start()` 不看该表自己的 `revision_days` | 9 个逐表覆写全部失效 → `stock_forecast` 查询区间退化成 `[T,T]` → **丢了整整一个月的预告** |
| 6 | `_period_skip` 自我续期（连 `⊘` 跳过也刷新 `finished_at`） | 快照表**永久冻结**（`index_weight` 冻了 53 个交易日） |
| 7 | 闸门 partial 连非日频表一起过滤掉 | 闸门一超时，**22 张非日频表一张都不跑**，日志只显示"其他频率 0 张" |
| 8 | 月频表丢了 `date_step="month"` 约定 | 月频表被当"按天查"，而数据打在每月 1 日 → **请求必然 0 行** |
| 9 | `trailing_nonzero_ratio` 分母自引用 | 分子恒等于分母 → 只能返回 0.0/1.0 → 稀疏表判据**不可达** → 白等 4 小时 |
| 10 | `delay_from_server_max` 把 `"有"` 当日期比大小 | `"有" >= "2026-09-14"` 恒真 → delay 观测恒为 0 → 自动标定形同虚设 |
| 11 | `delete_day` 的"防误删"检查在删除**之后** | 超限时日志说"跳过"，但数据**已经删了**；且该表不进台账 → **把 bug 掩盖成"没测"** |
| 12 | `delete-day --dry-run` 会写备份文件 | 一个声明"只打印不写"的开关，会覆盖上一轮的备份 |
| 13 | 部分失败（⚠️）不进 `alerts` | dump 配额用尽 / 区间失败都记 ⚠️，而退出码只看 `✘` → **机器可读的出口全是"成功"** |
| 14 | `fetch_all` 把服务端 `total` 谎报当成截断 | `399317.SZ` 报 13,428 行但只给 5,236 行 → 旧行为**丢弃这 5,236 行** |

**顺带修好的一个真洞**：`stock_history_5min` 的 09-14 本来只有 2,304 行（正常 266,400
= 5550 只 × 48 根），但 manifest 水位写着"已到 09-14" → dump 通道算出来"没有需要补的交易日"
⇒ **9 GB 的表会永远停在残缺口上**。回测删掉它之后水位退回 09-11，才启动补齐。

## 9. 已知边界（别把它们当 bug 查）

1. **上游真没数据**：`stock_forecast` 的 2026-08-13~09-14 —— 已直接请求上游确认返回 0 行，
   **别反复重试**。
2. **服务端 `total` 不可信**：`399317.SZ` 报 1.3 万行但实际只给 5 千行。`client.fetch_all`
   已改为"一页不满即视为给完了"，接受数据并记 `total_mismatch`（**不再丢数据**）。
3. **`dc_daily` T 当天时有时无**（实测同一时刻 09-11 → 1,031 行、09-14 → 0 行）。
   现行 `delay=0`，波动是常态；用户口径是"能拿就拿"，代价是那天厂商迟迟不发就要等。
4. **`daily_dump` 只能取最近约 90 天** —— 更早的 5min 缺口补不回。但这 90 天里取过的
   每一天都留了**本地原始件**，所以该范围内的重补不再依赖服务端、也不吃配额。
5. **per_entity 表的自愈深度 = 它的窗口**（`stock_cyq_chips` 是 3 个交易日）；
   更早的删除要用 `main.py delete-day --date <日期>` 显式修复。
6. **`stock_adj_factor` 有 545 格历史异常（全历史 14.37M 格中 453 格超 1e-3 红线）**：
   厂商偶发**除权调整晚一天进因子表**，或**多跳一次**。**不是我们抓错了**
   （尾部窗口每天重抓它、单日 MD5 台账也有），**不要试图"修"它**。
   复检在模块②：`featureengineering/scripts/check_adj_factor.py`（每月一次）。
7. **上游撤数（历史数据消失）—— 用户 2026-09-15 定策，务必照做**：
   > 「如果遇上了历史数据消失的情况，但是今天的 target 数据反而存在，那么只需要将新的数据
   > 合入数据集中。**不需要特意删除以前的数据**。但需要给这个消失的数据**打一个报告**即可。」

   - **合入新数据**：照常 upsert（新数据赢）——本来就是这个行为；
   - **本地旧数据一律保留**：写盘路径只有 `store.upsert()`，**没有任何删除逻辑**；
   - **打报告**：`report._vanished_notes` 输出
     `ℹ️ <表> <日期>：服务端该日已返回 0 行（上游撤数），本地保留 N 行**未删除**；上游恢复即自动更新`。
     判据两层：① 本次请求覆盖到这天；② 单日台账里这天**本地有行**、而服务端给 0 行。
   - 实测（2026-09-15）：`dc_daily` 的 09-14 被撤回后 20:45 又自己补回来了 —— 尾部窗口当天抓回，
     **因为本地那份从未被删、也从未被"补成空"**。
8. **备份是单日的**：`state/backtest/deleted_<表>__<日期>.parquet` 只保留最近一次同名删除。
   长期保护建议定期做硬链接快照（`cp -al`，零拷贝），写在 `state/backtest/full_<时间戳>/`。
   ⚠️ 硬链接快照是**当时状态**，之后厂商再改它也会跟着变 —— 要留中间态请用 `cp` 实拷或 `tar`。
9. **★ `stock_st_info`（15 号）厂商单表撤回 —— 2026-09-19 发现，尚未恢复**：
   厂商把 **2026-08-13 之后**的全部数据撤回了（服务端 max 从 09-18 **退到 08-12**）。
   - **不是我们的 bug**：09-18 22:13 的 `monitor` 记录里厂商仍有 09-18；本地 08-13~09-18
     行数逐日变化（206→205→203→204），是真抓的。同一时刻其它表（`stock_daily` 等）正常。
   - **本地数据不可复现**：厂商不再提供 ⇒ 本地那份是**唯一副本**（靠第 7 条"撤数不删本地"保住）。
   - **⚠️ 闸门会长期卡住**：它在**等待档**，服务端永不到齐 ⇒ 每轮日更白等
     `gate.max_wait_hours=6.0` 小时才 `on_timeout=partial` 放行。
     **临时对策**：`$PY main.py run --no-wait`。**根因对策待评估**（降档 / 加"厂商后退"检测），
     用户 2026-09-19 拍板"先只记录，不动代码"。
   - **建议厂商恢复后重测**：清空 `scripts/roundtrip_test.py` 的 `EXEMPT` 再跑一遍往返测试。
   - 完整证据链（逐条查询 + monitor 逐轮时间线）见 `state/backtest/REPORT_roundtrip_2026-09-18.md`。
10. **★ 25 号 `stock_pledge_stat` 的 `freq='quarterly'` 是误标 —— 它实际是「周频」**
    （2026-09-19 核查季频 21–25 时发现，**尚未修，待评估**）。
    - **证据**：`end_date` 从 **2025-08-15 起转为每周五**；2026 年 35 期连续完整
      （33 个周五 + 2 个周四顺延：`2026-04-30` / `2026-06-18`）；全历史 87 个日期里 **68 个是周五**。
      此前（2014~2025-08）确为稀疏的季末/月末，所以是老标定的遗留。
    - **影响 ①（观测档显示失真）**：`probe._watch_candidates`（`probe.py:452`）对
      `freq=='quarterly'` **只去问季末**（03-31/06-30/09-30/12-31）⇒ 闸门报
      "服务端最近有数据的一格 **2025-12-31**"，**而实际服务端有 2026-09-11**。
      （不误报落后：`behind` 用 local vs hit 同粒度比较，本地超前 ⇒ 判 False。）
    - **影响 ②（revision 过度）**：`revision_days=400` 是按季频设的，对周频表意味着
      每轮回刷 400 天（实测 **16 请求 / 16 秒**）。语义上过度，但不算事故。
    - **⚠️ 不要只改 `freq`**：`gate_tier`（`registry.py:196`）把
      `daily_full/daily_sparse/minute` 判为 **wait（阻塞）**、其余为 watch。
      25 号现在落在 watch 是对的 —— **必须保持不阻塞**（它每周才发一次，进 wait 会天天卡闸门）。
      而改成 `irregular` 又会让 `_watch_candidates` 走 else 分支（只问最近 3 个**交易日**），
      照样问不到周五的数据 ⇒ **正确修法需要一个「周频」候选期生成器**，不是一行改动。
    - **数据本身没问题**：服务端 2026-09-11 = 2219 行 = 本地 2219 行；
      服务端 2026-09-18 = **0**（厂商晚一期，09-18 是周五）⇒ **本地已跟到服务端最新可用期**。
11. **★ 21–24 号（4 张季频财报）：老期"滑出窗口就追不上"的问题已根治**（2026-09-19）
    —— **现在 main 每轮自动抓，不再需要人工审计**。
    - **更新逻辑**：`run_per_stock` 的 `REPORT_PERIOD_TABLES` 分支（`strategies.py:1177`）
      每轮**无条件**抓 `recent_report_periods(T, n=PERIOD_LOOKBACK=3)` —— 即 T 及以前最近 **3 个季末**，

## A.3 频率口径

**「日频」= 每个交易日都会产生新数据**，含 **18/19/20 三张分钟表**——它们同样每交易日更新，
只是日内有多根 bar，**在展示层归并进日频**。

> ⚠️ 但**注册表里的 `freq='minute'` 没有改**：`gate.py:126` 靠它走"完整性比例"闸门判据
> （防止盘中抓到的半份数据被判成就绪）。改成 `daily_full` 会退回普通判据，
> **盘中半份数据会被判成 ready**。⇒ 归并**只发生在展示层**，不动注册表。

**「快照」= 没有日期轴**，每次刷新整体替换。`28 basic_calendar` 特殊：**刻意更新到未来 T+30**，
供闸门回推 expected 日期。

## A.4 「不定期」（26 / 27 号）到底是什么意思

> **不定期 ≠ 更新频率低**，而是**没有固定日历节奏——由事件触发、由公司自己决定什么时候发**。

### 26 号 `stock_forecast`（业绩预告）— 按**财报季脉冲**

公司在**正式财报出来前**提前告诉市场"这一期大概赚多少"。字段：`type`（预增·略增·预减·首亏·
续亏·扭亏·略减·续盈·不确定·增亏·减亏·其他）/ `p_change_min,max`（同比变动%）/ `net_profit_min,max`
（净利润区间，万元）/ `last_parent_net` / `summary` / `change_reason`（长文本）/
`first_ann_date`（**首次**公告日，≠`ann_date` 即说明是**修正后**的）。

**为什么"不定期"**：交易所**强制**在特定条件下披露（净利润为负、扭亏、同比变动超 50%、微利…），
但**不是每只股票都发、也不是每个交易日都发**。全表 110,458 行 / 5,709 只 / 2010 起，
公告月分布是**四根尖峰**：

```
2026-01  3027  ████████████████████████  年报预告
2026-02    18  ▏
2026-04   228  ██                      一季报预告
2026-07  1813  ██████████████          中报预告
2026-10   136  █                       三季报预告
```

**1 月和 7 月占全年一半以上，2/3/5/6/8/9 月几乎为零。**

- ★ **PIT 陷阱**：必须用 **`ann_date`（公告日）** 对齐，**不能用 `end_date`（报告期）**——
  用 end_date 会把 1 月才知道的全年预告提前到 12-31，是**未来函数**。
- ★ **修正很多**：同一 `(stock, end_date)` 有 **7.8% 是多条**（公司改口，最多 4 条）；
  `first_ann_date != ann_date` 占 **9.3%**。取用要么取最新一条，要么用 `first_ann_date` 保留首发时点。

### 27 号 `stock_holder_number`（股东户数）— 定期报告 + 临时披露**混合**

只有 4 列：`stock_code` / `end_date`（时点，通常季末）/ `ann_date`（公告日）/ `holder_num`。
**户数变少 = 筹码集中**（散户离场、主力吸筹）；**变多 = 筹码发散**。常与 5 号 `stock_cyq_chips` 配合。

**为什么"不定期"**：披露时点**由公司自己定**，多数跟定期报告走，也有临时披露（回购、重大事项时
自愿公布）。比 26 号**均匀得多**——全表 427,830 行 / 6,060 只 / 2016 起，月月有量，
但 **4/8/10 月**（一季报/中报/三季报）明显是高峰（如 2025-04 有 14,786 行、2025-05 只有 2,288）。

**⚠️ 三个必须处理的数据陷阱**（实测）：

1. **`holder_num == 0` 是缺失占位，不是真的"0 个股东"**——全表 **20,417 行 = 4.77%**
   （如 `002936.SZ 2018-09-18`）。**取用前必须 `holder_num > 0` 过滤**。
2. **`end_date == ann_date` 占 4.81%**（20,584 行）——正常 end_date 应是季末，相等说明时点可疑
   （疑似厂商用公告日占位）。做时序对齐建议只留 end_date 是月末的行。
3. **同一只股票最多 423 行**（中位数 45 行）——远超"每季度一条"，说明同一 `end_date` 被反复公告。
   **去重建议 `(stock_code, end_date)` 取 `ann_date` 最大的一条。**

### 为什么 26/27 不进 delay 观测

`pipeline/monitor.py:41` 只收**真正的日历轴**字段：

```python
_MONITOR_DATE_FIELDS = ("trade_date", "date", "report_date", "trade_time")
```

26 号的 `date_field=ann_date`、27 号的 `date_field=end_date` **都不在白名单里**——对"公告日/报告期"
问"服务端某天有没有数据"**没有意义**（不是每个公告日都该有数据），只会把观测变成噪声。
所以它们的 revision 由 `registry.py` 手工标定：26 号 **90 天**（上游确实常空，**别重试**）；
27 号台账键用 `ann_date`、**400 天**。

### 2. 这个数据集是什么

`datadownload/data/stock_holder_number/` —— **股东户数**（每家公司的持股账户数）。

| 列 | 含义 | 大白话 |
|:--|:--|:--|
| `stock_code` | 股票代码 | |
| **`end_date`** | **统计截止日** | 「这个数字，是**统计到哪一天为止**的」 |
| **`ann_date`** | **公告日** | 「这家公司是**哪天把这个数字说出来的**」 |
| `holder_num` | 股东户数 | |

规模：**427,594 行 / 11 个年分区 / 3,595 个不同的 `ann_date`（2016-01-04 起）**

#### ★★ 核心性质：**只增不减**

**关键：`end_date` 与 `ann_date` 不是同一天，而且同一个 `end_date` 会被由不同公司
在很长的时间跨度内陆续披露。**

打比方：学校在 3 月 31 日做了一次点名（「截至 3 月 31 日，我们班 45 人」），
但**不是当天就公布** —— 有的同学 4 月 15 日才说、有的 4 月 29 日才说。
股票这边一模一样：每家公司各自挑日子说。

**实测（`end_date=2026-09-10` 这一格的公告节奏）**：

| 公告日 | 公司数 |
|:--|--:|
| 2026-09-09 | 1 |
| 2026-09-10 | 2 |
| **2026-09-11** | **160** |
| 2026-09-12（周六） | 4 |
| 2026-09-13（周日） | 1 |
| **2026-09-14** | **133** |
| **2026-09-15** | **175** |
| **2026-09-16** | **152** |

⇒ **这一格到今天还在长**（449 → 628 行就是 09-16 又来了 152 家）。

### 3. 为什么它被列进黄名单

#### ① 「历史不变」这条不变量**对它不适用**
它是只增不减的表（见上）。任何「某天的值会冻结」的假设都是错的。

#### ② MD5 台账对它**从设计上就失效**（关键）
台账用 `end_date` 做日期键，而 `end_date` 桶**永远在长** ⇒ **每跑必报红，报红是常态**。

> **这比"没有保护"更危险**：台账的全部价值在于「只有异常才报」。
> 对它失效，等于**真出问题时会被淹没在每天的噪声里**。
> 证据：2026-09-16 那轮报的 `stock_holder_number 2026-09-10 行数 449→628`
> 就是常态，**不是异常**。

#### ③ **4.775% 是零值占位行**（20,416 行 / 2,047 只股）
- `holder_num == 0`（零股东户数**物理上不可能**）
- **93% 集中在 2026 年**（18,976/20,416）
- **91.6% 满足 `ann_date == end_date`**（全表仅 4.8%）→ 像是厂商对"该期无数据"返回的**同日占位行**
- 950 个 `(股票, end_date)` 组合**同时有 0 和真实值** → 占位行后来被真实披露覆盖
- **下游必须过滤**（`holder_num > 0`，因子已这么做）

#### ④ 30 行（0.007%）超出抓取窗口 —— **永久缺口**
`_REVISION["stock_holder_number"] = 400` 天，而实测最长公告滞后 **1,098 天**
⇒ 超过 400 天的那批**永远抓不到**。

#### 为什么它跟那 6 张 delay 表待遇不同（都是"工具问题"，它们升绿、它留黄）
| | 6 张 delay 表 | `stock_holder_number` |
|:--|:--|:--|
| 工具缺口位置 | `monitor` 的**标定逻辑**（独立工具） | **MD5 台账**（红线赖以存在的**核心保障**） |
| 后果 | 标定建议不可信，数据与台账都正常 | 台账对这张表**无法工作**，红线失去常驻证据 |

⇒ **6 张是"工具在别处有缺口"；这张是"数据形态与完整性模型本身不兼容"。**

### 4. 改造设计（用户 2026-09-16 拍板）

**用户原话要害**：「只需要改台账的统计逻辑就行了」+「换了新的台账算法后跟踪几天再看看」
+ 「截止日期固定，不同的公司会在这个截止日期未来的某一天说出一个数据……
   **如果以当天汇报了多少数据这个维度来统计不就行了吗**」。

**⇒ 台账键 `end_date` → `ann_date`。** 理由：`ann_date` 是**封闭事件**
（那天发了多少条），那天过了就定稿；`end_date` 是**开放累计量**，永远在长。

`ann_date` 维度质量实测：**空值/非法 0 行 · 未来日期 0 行**。

#### 关键约束：**绝不改抓取语义**
`date_field` **同时被用于抓取窗口计算**，不能动。所以给 `DS` 加了三个
**默认保持现状**的开关，只对声明了的表生效：

```python
ledger_field: str = ""              # "" = 用 date_field（所有其它表的现状）
ledger_calendar_days: bool = False  # 窗口用日历日（公告日含周末）
ledger_lag_days: int = 0            # 比对滞后（公告当天厂商可能几小时后才挂出）

def ledger_date_field(self) -> str:
    return self.ledger_field or self.date_field
```

**为什么需要 `ledger_calendar_days`**：公告日**含周末**（实测 09-12 周六 4 条、
09-13 周日 1 条），而尾部窗口默认只取**交易日** → 那几格永远不被指纹化 → 台账漏天。

**为什么需要 `ledger_lag_days`**：上一次爬取在 09-16 **00:22**，今天 22:21 那次对
`end_date=09-10` 多拿了 179 行，其中 152 行是 `ann_date=09-16`（符合预期），
但约 **27 行的 `ann_date ≤ 09-15`** —— **当晚发出、过了午夜才挂到接口上**。
这与 `stock_margin_detail` 的 `delay=1` 是**同一类问题**（"数据到达晚"），
故沿用**同一套修法**：比对滞后 1 天。

#### 唯一被声明的表

```python
_reg(DS(name='stock_holder_number', ..., date_field='end_date',
```

### 6. ★★ 顺带暴露出的既有 bug（**已修**）

#### 症状
换键后重建台账，只建出 **3,551 天**，而数据里有 **3,595 个 `ann_date`** → 差 **44 天**。
深检报：`⚠️ stock_holder_number 数据里有但台账没有：['2018-01-01','2018-01-03','2018-01-05',…]`

#### 根因
**台账代码一直假设「日期的年份 == 分区年份」**（`partition_path(ds.name, int(date[:4]))`）。

- 分区是按**抓取键**（`date_field='end_date'`）的年份切的
- 台账按 **`ledger_field='ann_date'`** 取键
- 两者不同 ⇒ 假设破裂

**实测铁证**：
```
ann_date = 2018-01-01 的那条记录，其 end_date = 2017-12-29
→ 它住在 year=2017 分区里
→ 而 _read_day('2018-01-01') 去翻 year=2018 → 找不到
```
```
year=2017 分区：ann_date 年份 = ['2016','2017','2018']   ← 跨了三个年份！
year=2018 分区：ann_date 年份 = ['2018','2019']
```

**这个假设对所有 `ledger_field == date_field` 的表都成立**，所以从没暴露 ——
是这次换键把它翻出来的。44 天**全是跨年边界**的那些。

#### 修法
新增 `_candidate_files(dataset, ds, years)`：
- **快路径**（`ledger_field == date_field`）：只读该日期年份的分区 —— **与改前逐字等价**，性能不变；
- **慢路径**（两者不同）：**扫全部分区**。这类表目前只有 `stock_holder_number`
  （11 分区 / 42.7 万行，全扫代价可忽略），**不会拖慢** `stock_cyq_chips` / `stock_history_5min` 那种大表。

`_read_day` / `_read_days` / `data_days` 三处均改用 `_candidate_files`。
`_read_days` 还重构成「快路径按年单读 / 慢路径一次扫全部并切全部目标日」两条清晰分支
（初版写成从文件路径字符串里解析年份，太脆，已重写）。

#### 修复验证
```
修复前：台账 3,551 天
修复后：台账 3,595 天   ← 与数据里 3,595 个 ann_date 完全对齐 ✔
单点：_read_day('2018-01-01') → 1 行 ✔ · ('2018-01-03') → 90 行 ✔ · ('2025-01-25') → 5 行 ✔
```

### 4. 破坏性实测：删掉所有文件最新一天 → 重爬 → 验收

#### 4.1 步骤（可复现）

```bash
cd /autodl-fs/data/everyday_tasks
PY=/autodl-fs/data/miniconda3/bin/python
cp -al /autodl-fs/data/datadownload/data state/backtest/full_<ts>/data   # 硬链接快照（2 秒 / 零拷贝）
$PY main.py backtest baseline            # ① 记各表最新一天的指纹（30 张 / 1m34s）
$PY main.py delete-day                   # ② 删各表**自己的**最新一天（30 张 / 666,818 行 / ~2.5min）
$PY main.py run --as-of 2026-09-16       # ③ 重爬（★ 用自带测试模式，见下）
$PY main.py backtest verify              # ④ 逐表比对
```

- **为什么删"各表自己的最新一天"**：有 delay 的表（`stock_margin_detail` 等）最新数据本来就晚一天，
  统一删某一天会整批跳过它们 —— 而它们恰恰最脆弱（`BACKTEST_REPORT.md` 有完整论证）。
- **为什么用 `--as-of 2026-09-16`**：实测时是 09-17 上午，盘中；让 `resolve_T` 自然探测
  有概率把 09-17 的**半份数据**写进所有日频表。`--as-of` 是项目自带的测试模式（用已确认完整的日期当 T）。
- 实际删到的日期：23 张删 `09-16`、4 张季报删 `06-30`、`holder_number` 删 `09-10`、
  `pledge_stat` 删 `09-11`、`margin_detail` 删 `09-15`。

#### 4.3 两处差异的定性（**都是真信号，不是回归**）

1. **`stock_daily`/`stock_finance` 只有 `stock_name` 变了** —— 厂商今早**回溯改写**了近期新股名称。

   | 股票 | 昨天 | 今天 |

   行数不变、只有值变 = 厂商重算，属报告里那类 🔴（记录即可，不用处理）。

2. **4 张季报的 ✘ 是回测工具口径问题**（数据补得好好的）：它们**抓取轴是 `end_date`、
